☁️Azure Diagnóstico

Guía para diagnosticar problemas de rendimiento con herramientas Azure

Resumen

Esta guía explica cómo utilizar Azure herramientas de diagnóstico para analizar los problemas de rendimiento simulados por esta aplicación.

🔗 Correlación ID de simulación

A cada instancia de simulación se le asigna un ID de simulación único (GUID) que permite una correlación de extremo a extremo entre la interfaz del panel de control y la telemetría Azure Application Insights .

Encontrar identificadores de simulación

En el panel de control: Los mensajes de inicio y finalización de simulación en el Registro de Eventos tienen una subrayado punteado sutil que indica que son interactivos. Pasa el cursor sobre estos mensajes para ver el contenido completo ID de simulación en una descripción emergente. Haz clic para copiarlo en tu portapapeles.

En Azure: El mismo ID de simulación se emite en los registros del lado del servidor y puede encontrarse en:

  • Application Insights — Trazas de búsqueda y eventos personalizados por ID de simulación
  • Análisis de registros — Registros de consulta usando el ID como filtro
  • App Service Registros — Filtra stdout/stderr por el GUID

// Find simulation start/end events by Simulation ID
AppEvents
| where Name in ("SimulationStarted", "SimulationEnded")
| where Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
| project TimeGenerated, Name, Properties
| order by TimeGenerated asc
// Find all requests during a simulation time window
let simStart = toscalar(
    AppEvents 
    | where Name == "SimulationStarted" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
let simEnd = toscalar(
    AppEvents 
    | where Name == "SimulationEnded" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| order by TimeGenerated asc
// Find failed requests during a simulation
let simId = "YOUR-SIMULATION-ID-HERE";
let simEvents = AppEvents | where Properties["SimulationId"] == simId;
let simStart = toscalar(simEvents | where Name == "SimulationStarted" | project TimeGenerated);
let simEnd = toscalar(simEvents | where Name == "SimulationEnded" | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| where Success == false
| project TimeGenerated, Name, ResultCode, DurationMs, Url
| order by TimeGenerated asc

Flujo de trabajo de resolución de problemas

  1. Inicia una simulación desde el panel de control
  2. Pasa el cursor sobre el mensaje de inicio en el Registro de Eventos para copiar el ID de Simulación
  3. Portal abierto Azure → Application Insights → Registros (o Análisis de Registros)
  4. Consulta los registros usando el ID de simulación para ver toda la actividad relacionada del lado del servidor
  5. Correlacionar las marcas de tiempo entre eventos del panel de control y métricas del servidor

💡 Propina

El ID de simulación ayuda a aislar la telemetría al ejecutar múltiples simulaciones simultáneas o cuando el panel de control es utilizado por varios usuarios.

AppLens Integración

Esta aplicación está diseñada para funcionar con Azure AppLens enviando sondas de salud cada 100 ms a través del frontend de Azure sello. Esta sondeo de alta frecuencia garantiza que la latencia aumente y Los problemas de disponibilidad son visibles en AppLens paneles.

Lo que AppLens puede detectar

  • CPU Estrés: Gráficos de alta utilización de CPU , posibles alertas de limitación
  • Presión de memoria:Picos de uso de memoria, patrones de potencial OOM
  • Privación de hilos: Mayor latencia de solicitudes, cola de peticiones
  • Fondo de conexiones: Los volcados de hilos muestran el estado ESPERANDO, errores de tiempo de espera
  • Solicitudes fallidas:HTTP picos de error 5xx, caídas de disponibilidad, incrementos en la tasa de error
  • Accidentes: La instancia se reinicia, la disponibilidad cae

Azure Monitorizar métricas

Métricas clave a vigilar en Azure Monitor al ejecutar simulaciones:

Métricas de plataforma

  • CPU Porcentaje: Observa picos durante simulaciones de CPU esfuerzo
  • Conjunto de trabajo de memoria: Aumentos durante simulaciones de presión de memoria
  • HTTP Longitud de la cola: Crece durante la falta de hilo
  • Tiempo de respuesta: Cuidado con aumentos de latencia en P95/P99
  • Http 5xx: Aumentos durante solicitudes fallidas y simulaciones de fallo

Métricas de JVM (si App Insights está habilitado)

  • jvm_memory_used: Memoria heap y no heap
  • jvm_gc_pause:GC pausas
  • jvm_threads_live: Conteo de hilos activos

Application Insights

Si Application Insights está configurado, puedes usar estas funciones:

Transmisión de métricas en directo

Observa métricas en tiempo real durante las simulaciones:

  1. Navega hasta tu App Service en Azure Portal
  2. Ve a Application Insights → Live Metrics
  3. Observa CPU, memoria y tasas de solicitud en tiempo real

Búsqueda de transacciones

Encuentra solicitudes lentas o fallidas:

  1. Ve a Application Insights → Búsqueda de transacciones
  2. Filtra por "Solicitudes fallidas" o "Tiempo de respuesta del servidor > 5s"
  3. Profundiza en solicitudes individuales para ver el desglose temporal

Mapa de aplicaciones

Visualiza la salud y dependencias del servicio:

  1. Ir a Application Insights → Mapa de Aplicaciones
  2. Busca indicadores rojos/amarillos durante las simulaciones
  3. Comprueba si hay más tasas de fallo o latencia

Diagnosticar y resolver problemas

Azure App Service proporciona herramientas de diagnóstico integradas:

Disponibilidad y rendimiento

  1. Ve a App Service → Diagnosticar y resolver problemas
  2. Selecciona "Disponibilidad y Rendimiento"
  3. Consulta "HTTP 5xx Errores" para problemas relacionados con los cuelgues
  4. Marca "High CPU" para detectar CPU estrés
  5. Comprueba "Memoria" para detectar la detección de presión de memoria

Herramientas de diagnóstico

  • CPU Profundiza en detalle: Consulta CPU desglose de uso por instancia
  • Volcado de memoria: Volcado de captura de heap durante problemas de memoria
  • Volcado de hilos: Captura de pilas de hilos durante la inanición
  • JFR (Grabador de vuelo Java): Aplicación Java de perfiles

Análisis de Registros / Consultas KQL

Consultas útiles de KQL para analizar efectos de simulación:

Peticiones de CPU altas

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where ScStatus >= 500
| summarize Count=count() by bin(TimeGenerated, 1m)
| render timechart

Tiempos de respuesta lentos

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where TimeTaken > 5000
| project TimeGenerated, CsUriStem, TimeTaken, ScStatus
| order by TimeTaken desc

Patrón de uso de memoria

AppServicePlatformLogs
| where TimeGenerated > ago(1h)
| where Level == "Informational"
| project TimeGenerated, Message
| order by TimeGenerated desc

Diagnósticos específicos de Java

Habilitar JMX para monitorización remota

Añade estos ajustes de la app para acceso a JMX (solo desarrollo):

JAVA_OPTS=-Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9010 \
  -Dcom.sun.management.jmxremote.local.only=false \
  -Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false

Habilitar GC registro

JAVA_OPTS=-Xlog:gc*:file=/home/LogFiles/gc.log:time,level,tags

Descargas de montones sobre OOM

JAVA_OPTS=-XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/home/LogFiles/heapdump.hprof

Volcados de hilo de lectura: Agotamiento de la piscina de conexión

Al diagnosticar problemas en el pool de conexiones, busca hilos en TIMED_WAITING Estado bloqueado en la adquisición de recursos:

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)

Ejemplo real de HikariCP:

"http-nio-8080-exec-15" TIMED_WAITING
    at com.zaxxer.hikari.pool.HikariPool.getConnection(...)
    at com.zaxxer.hikari.HikariDataSource.getConnection(...)

Lo que dice el hilo significa:

  • CORRIENDO — Ejecución activa (CPU trabajo)
  • BLOQUEADO — Esperando un bloqueo de monitor (bloque sincronizado)
  • ESPERANDO — Esperando indefinidamente (Object.wait, Thread.join)
  • TIMED_WAITING — Esperar con tiempo muerto (común en los tiempos muertos en la piscina)

Muchos hilos en TIMED_WAITING sobre adquisición de pool = agotamiento de pool de conexión. Aumenta el tamaño del grupo o reduce el tiempo de espera de consultas.

Mejores prácticas

Empieza poco a poco

Comienza con simulaciones de corta duración (10-30 segundos) y baja intensidad (2-4 trabajadores, 100-200MB de memoria) para entender el impacto de referencia antes de escalar.

Monitorizar antes de simular

Establece una línea base observando métricas durante unos minutos antes Iniciando cualquier simulación. Esto facilita identificar los cambios.

Precaución de producción

Nunca realices simulaciones de fallo ni pruebas de estrés de alta intensidad en producción entornos. Usa los espacios de preparación/desarrollo para las pruebas.
