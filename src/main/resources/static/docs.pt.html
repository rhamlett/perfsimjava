🎯 Simulador de Problemas de Desempenho

Uma aplicação Azure App Service educacional que intencionalmente cria problemas de desempenho para fins de aprendizagem e demonstração.

Propósito

Esta aplicação foi projetada para ajudar Azure App Service Engenheiros de Suporte e Consultores Técnicos:

📖
Aprenda

Como diagnosticar problemas comuns de desempenho em Azure App Service

🔧
Prática

Usando Azure ferramentas de diagnóstico e monitoramento

🎭
Demonstrar

Anti-padrões de desempenho em um ambiente controlado

👥
Trem

Apoiar as equipes na identificação e resolução de problemas de desempenho

⚠️ Aviso — Este aplicativo cria problemas de desempenho intencionalmente!
  • 🔥 CPU estresse — Gera threads de trabalho rodando operações criptográficas para consumir CPU núcleos
  • 📊 Pressão de memória — Aloca e mantém grandes arrays de bytes para aumentar o uso do heap
  • 🟣 Privação de fios — Bloqueia threads servlet com operações síncronas
  • 🔌 Exaustão do pool de conexão — Simula saturação da pool de conexão JDBC
  • 💥 A aplicação trava — Aciona erros fatais para testes Azure Monitoramento de Acidentes
  • ❌ Pedidos fracassados — Gera erros HTTP 5xx para testes de AppLens e Application Insights
🛡️ Aviso de Segurança: Implante essa aplicação apenas em ambientes isolados e não produtivos.

CPU Simulação de Estresse

Como Funciona

A simulação de CPU tensão cria threads de trabalho que funcionam PBKDF2WithHmacSHA512 operações criptográficas — trabalho computacionalmente caro que não pode ser otimizado pelo compilador JIT.

Entendendo a Simulação

Cada thread de trabalho funciona em um ciclo apertado realizando operações de hash de senha. Isso imita cenários do mundo real como:

  • Algoritmos ineficientes — loops O(n²) ou retrocesso regex
  • Caches ausentes — Recalculando operações caras repetidamente
  • Malware de mineração de criptomoedas— Consumo não autorizado de CPU
  • Consultas não otimizadas — Processamento de dados CPUlimitado

Opções de configuração

  • Duração (segundos) — Quanto tempo o estresse dura antes de parar automaticamente.
  • Intensidade — Escolha Alto ou Moderado para controlar CPU nível de consumo.

O que você verá em diagnósticos

  • Despejos de threads: Threads em RUNNABLE Estado dentro PBKDF2Core ou SecretKeyFactory
  • CPU Perfilador: Amostras de alto CPU em classes criptográficas
  • App Service Métricas:CPU pico percentual durante a simulação

Controles do Painel

Use o CPU Estresse painel no painel para iniciar/parar simulações. Selecione nível de intensidade e duração, depois clique Gatilho CPU Estresse.

Simulação de Pressão de Memória

Como Funciona

A simulação de memória aloca grandes arrays de bytes que permanecem armazenados no heap até serem liberados explicitamente, impedindo que a coleta de lixo recupere a memória.

Entendendo Vazamentos de Memória

Em aplicações reais, vazamentos de memória ocorrem quando objetos permanecem acessíveis, mas não são mais necessários. Causas comuns incluem:

  • Coleções estáticas — Somando a um estático List ou Map sem remover
  • Ouvintes do evento — Registrar ouvintes que nunca são desregistrados
  • Caches sem expulsão — Caches ilimitados que crescem indefinidamente
  • Variáveis ThreadLocal — Valores mantidos em threads agrupados
  • Dados da sessão— Grandes objetos armazenados em sessões HTTP

Opções de configuração

  • Tamanho (MB) — Quantidade de memória heap para alocar por clique. Múltiplas alocações se empilham.

O que você verá em diagnósticos

  • GC Frequência: Aumento da atividade GC à medida que o monte se enche
  • Despejos de pilha: Grande byte[] Arrays mantidos pelo serviço de simulação
  • Métricas de Memória: Uso do heap subindo em direção ao alvo configurado
  • GC Pausa: Mais tempos GC à medida que o heap se aproxima da capacidade

Controles do Painel

Use o Memória painel no painel para alocar memória e observar o uso do heap crescer em tempo real. Click Lançamento para liberar toda a memória alocada sob demanda.

Simulação de Inanição de Pool de Fios

Nota: Este é o equivalente em Java ao "Bloqueio de Loop de Eventos" em Node.js. Como o Java usa um modelo thread-per-request, bloquear múltiplos servlets threads simula O mesmo sintoma de fila de requisições e picos de latência.

Entendendo a Duração e a Contagem de Fios

A simulação gera solicitações internas de HTTP que bloqueiam cada uma uma thread de servlet. Veja como o tempo funciona:

  • Duração por solicitação: Cada solicitação de bloqueio roda pela duração especificada (por exemplo, 10s)
  • Pool de tópicos Tomcat: Padrão máximo ~200 threads
  • Comportamento das ondas: Se você gerar mais threads do que o tamanho do pool, pedidos excedentes ficam na fila HTTP do Tomcat

Exemplo de linha do tempo (220 threads, duração de 10s):

Tempo O que acontece
0-10s Primeiras 200 solicitações, agarre threads, comece a bloquear. 20 pedidos esperando na fila.
~10s Primeira onda completa. Com 20 pedidos na fila, agora recebem tópicos.
~Anos 20 A segunda onda termina. Simulação termina.

Fórmula: Tempo total ≈ durationSeconds × ⌈threadCount / 200⌉

Opções de configuração

  • Fios Bloqueados — Número de solicitações de bloqueio a serem geradas
  • Duração (segundos) — Quanto tempo cada requisição bloqueia seu thread

Configurações recomendadas:

  • Teste rápido: 150 fios, 10s (onda única, ~10s no total)
  • Impacto moderado: 200 roscas, 15s (satura pool, ~15s no total)
  • Teste estendido: 400 roscas, 10s (duas ondas, ~20s no total)

O que você verá em diagnósticos

  • Despejos de threads: Muitos fios em TIMED_WAITING Estado
  • Picos de latência: Novas requisições ficam em fila atrás de threads bloqueadas
  • Painel: A contagem de fios ativos sobe rapidamente

Exaustão da Piscina de Conexão

Entendendo Pools de Conexão

Pools de conexão de banco de dados (como HikariCP, C3P0, Tomcat JDBC) mantêm um número fixo de conexões reutilizáveis de banco de dados. Quando todas as conexões estão em uso, novas solicitações precisam esperar. Esse é um dos problemas de desempenho mais comuns em aplicações Java.

Como Essa Simulação Funciona

Nós usamos um Semáforo — uma primitiva de concorrência Java que controla o acesso a um número limitado de recursos. Pense nisso como um estacionamento:

  • Tamanho da Piscina = Número de vagas de estacionamento
  • acquire() = Carro ocupa um espaço (faz uma conexão)
  • Lançamento() = Carro sai (retorna conexão ao pool)
  • Threads de espera = Carros na fila no portão quando o estacionamento está lotado

Semáforo → Mapeamento HikariCP:

new Semaphore(10) maximumPoolSize=10
tryAcquire(30, SECONDS) connectionTimeout=30000
release() Conexão retornada ao pool
Thread bloqueado ao adquirir Thread aguardando conexão disponível

Opções de configuração

Ajustável pelo painel:

  • Tamanho da Piscina — Número de conexões simuladas disponíveis
  • Duração da consulta (segundos) — Quanto tempo cada \"consulta\" mantém uma conexão
  • Consultas Simultâneas — Número de consultas simultâneas a serem tentadas
  • Tempo de Conexão (segundos) — Quanto tempo esperar antes de expirar o tempo

O que você verá em despejos de tópicos

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)
    at com.microsoft.azure.samples.perfsimjava.service.ConnectionPoolService.executeQuery(...)
    ...

Em aplicações reais, isso mostraria HikariPool.getConnection() ou BasicResourcePool.getResource() em vez disso.

Indicadores Diagnósticos

  • Dumps de threads mostrar threads TIMED_WAITING em Semaphore.tryAcquire
  • Picos de latência quando threads servlet bloqueiam a espera de conexões
  • Erros de tempo de espera quando a espera excede o tempo de espera configurado
  • O painel mostra a utilização em tempo real do pool e a contagem de tempo limite

Simulação de Solicitações Falhadas

Como Funciona

A simulação de Solicitações Falhadas gera HTTP erros 5xx ao fazer requisições internas ao endpoint do teste de carga com probabilidade de erro de 100%. Cada requisição gera um erro visível no servidor que aparece nos diagnósticos Azure .

Entendendo HTTP Erros 5xx

HTTP erros 5xx indicam falhas no lado do servidor. Esta simulação ajuda você a praticar a identificação e diagnóstico de padrões de erro usando Azure ferramentas:

  • AppLens:HTTP erros 5xx aparecem na linha do tempo de disponibilidade e nos relatórios de erros
  • Application Insights: Solicitações fracassadas são acompanhadas com detalhes completos de exceção
  • Azure Monitor: A métrica http5xx aumenta, acionando quaisquer alertas configurados
  • Análise de Log: Detalhes do erro disponíveis via consultas KQL

Opções de configuração

  • Número de Solicitações — Quantas requisições falhadas devem ser geradas (1-1000, padrão: 10)

O que você verá em diagnósticos

  • AppLens:HTTP pico de erro 5xx no cronograma, queda na disponibilidade
  • Application Insights: Requisições falhadas com tipos de exceção como TimeoutException, IOException
  • Azure Monitor: Aumento da métrica Http5xx
  • Latência de Solicitação: Cada requisição leva ~2+ segundos para ser executada antes de falhar

API Endpoint

POST /api/simulações/solicitações-falhadas

Aciona um lote de HTTP solicitações de erro 5xx.

Corpo do Pedido:

{
    "numberOfRequests": 10
}

Resposta:

{
    "simulationId": "abc123",
    "type": "FAILED_REQUESTS",
    "numberOfRequests": 10,
    "status": "RUNNING",
    "message": "Generating 10 failed HTTP requests"
}

Controles do Painel

Use o Pedidos Fracassados painel no painel para gerar erros. Insira o número de solicitações e clique Gerar erros. A simulação é executada rapidamente e produz HTTP respostas 5xx visíveis em Azure ferramentas de diagnóstico.

Simulação de Colisão

Aviso: Essas simulações travam ou encerram a aplicação. Use apenas para testar diagnósticos e cenários de recuperação em App Service.

Tipos de Colisão Disponíveis

Selecione um tipo de falha no painel para testar diferentes modos de falha:

🛑 Falha Rápida (System.exit)

Termina imediatamente a JVM com System.exit(1). O processo sai sem rodar ganchos de paralisação ou finalizadores. Em App Service, isso desencadeia uma reinicialização imediata.

📉 Excesso de Pilha

Aciona um StackOverflowError por recursão infinita. Isso simula bugs como chamadas circulares de métodos ou recursão ilimitada. O rastreamento de pilha mostrará chamadas repetidas para o mesmo método.

⚠️ Exceção Não Tratada

Joga um sem controle RuntimeException De um responsável por solicitações. Testa como sua aplicação lida com erros inesperados e se o middleware de gerenciamento de exceções está funcionando corretamente.

💥 Fora de Memória (OOM)

Aloca memória rapidamente até que a JVM emita um OutOfMemoryError. Isso é útil para testar:

  • App Service comportamento de reinício automático no OOM
  • Alerta e monitoramento de memória
  • Configuração de coleta de dump de heap

Configuração Opcional

Você pode personalizar o comportamento da aplicação usando Azure App Service variáveis de ambiente.

Taxa de Sondagem de Saúde

Controle com que frequência o servidor envia sondas de saúde para medir a latência das requisições. Todas as sondas são roteadas pelo frontend Azure para capturar latência realista de ponta a ponta.

Variável Ambiente

Nome da variável Descrição Padrão
HEALTH_PROBE_RATE Intervalo de sonda em milissegundos. Mínimo 100ms. 200

Configuração via Azure CLI

# Slow down probes if CLR profiler shows overlapping requests
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings HEALTH_PROBE_RATE=400

Tempo de inatividade

Quando a aplicação está ociosa (sem conexões no painel ou requisições de teste de carga), as sondas de saúde são automaticamente suspensas para reduzir o tráfego desnecessário de rede para a interface e a telemetria Application Insights da Azure.

Variável Ambiente

Nome da variável Descrição Padrão
IDLE_TIMEOUT_MINUTES Minutos de inatividade antes de suspender as sondas de saúde. A atividade é retomada automaticamente quando o painel é aberto ou qualquer solicitação é recebida. 20

Configuração via Azure CLI

# Extend idle timeout to 30 minutes
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings IDLE_TIMEOUT_MINUTES=30

Rodapé de página personalizado

Defina uma mensagem personalizada no rodapé que apareça em todas as páginas. O rodapé suporta HTML, permitindo incluir links.

Variável Ambiente

Nome da variável Descrição
PAGE_FOOTER Conteúdo HTML para a segunda linha do rodapé. Se não estiver definido, apenas a descrição do app e as informações da build são mostradas.

Exemplo de Valor

Created by <a href="https://yoursite.com">Your Team</a> for training purposes

Configuração via Azure CLI

# Set the footer via Azure CLI
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings 'PAGE_FOOTER=Created by <a href="https://yoursite.com">Your Team</a> for training purposes'

Ambientação via Azure Portal

  1. Navegue até sua App Service no Portal Azure
  2. Vá para Configurações → Variáveis do ambiente
  3. Click + Adicionar
  4. Nome do Conjunto: PAGE_FOOTER
  5. Valor de Definição: Seu conteúdo do rodapé HTML
  6. Click Candidate-se, então Confirme

GitHub Link do Repositório

Por padrão, o link GitHub Repositório no menu lateral está oculto. Defina ambas as variáveis de ambiente abaixo para exibir um link para seu repositório de GitHub no menu de navegação.

Variáveis Ambientais

Nome da variável Descrição
GITHUB_USER_NAME O GitHub nome de usuário ou organização que é dona do repositório.
GITHUB_REPO_NAME O nome do repositório GitHub .

Exemplo

Para linkar https://github.com/myorg/myrepo, set:

  • GITHUB_USER_NAME=myorg
  • GITHUB_REPO_NAME=myrepo

Configuração via Azure CLI

# Set the GitHub repository link
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings GITHUB_USER_NAME=myorg GITHUB_REPO_NAME=myrepo

Arquitetura

A aplicação roda como uma aplicação Spring Boot 3.3 com Tomcat incorporado, STOMP over WebSocket para métricas em tempo real e estado em memória. Um serviço dedicado de sonda mede a latência da solicitação sondando o aplicativo através do frontend da Azure.

Componentes Principais

  • Aplicação Spring Boot— Servidor Tomcat embarcado com controladores REST e suporte a WebSocket
  • Serviço de sonda— Tarefa agendada em segundo plano que mede a latência do pedido enviando HTTP sondas pela interface Azure
  • Serviços de Simulação — CPU simulações de estresse, pressão de memória e bloqueio de threads rodam em pools dedicados de threads para evitar privar os threads servlet
  • WebSocket Corretor — Mensagens STOMP via SockJS para atualizações em tempo real do painel (métricas, eventos, status da simulação)

🌐 Seleção de Língua

A interface do painel pode ser exibida em qualquer idioma suportado por Azure Tradutor de Serviços Cognitivos. A tradução é realizada uma vez na inicialização da aplicação e armazenada em cache — não há nenhuma sobrecarga de tradução em tempo de execução.

Como Funciona

  1. Defina o UI_LANGUAGE Variável ambiente para um código de idioma ISO 639-1 (por exemplo, es, fr, ja, zh-Hans)
  2. Forneça credenciais Azure tradutor via variáveis de ambiente
  3. Ao iniciar, o app traduz todas as strings da interface (en.json → {lang}.json) e páginas de documentação HTML
  4. Arquivos traduzidos são armazenados em cache com um hash SHA-256 da fonte — eles só são retraduzidos quando a fonte muda

Variáveis Ambientais Obrigatórias

Variável Descrição Padrão
UI_LANGUAGE Código no idioma alvo en (sem tradução)
TRANSLATOR_API_KEY Azure Tradutor API chave —
TRANSLATOR_ENDPOINT Endpoint de serviço tradutor https://api.cognitive.microsofttranslator.com
TRANSLATOR_REGION Azure região do recurso Tradutor eastus

Azure App Service Configuração

No portal Azure , vá até sua App Service → Configuração → Configurações de aplicação e acrescentar:

UI_LANGUAGE=es
TRANSLATOR_API_KEY=your-key-here
TRANSLATOR_REGION=eastus

Termos Protegidos

Termos técnicos listados em locales/no-translate.json (por exemplo, "Azure App Service", "CPU", "JVM", "STOMP") são automaticamente incluídos em <span class="notranslate"> tags antes da tradução, garantindo que permaneçam em inglês independentemente do idioma de destino.

Comportamento do Cache

  • Arquivos de localização traduzidos são armazenados como locales/{lang}.json (por exemplo, locales/es.json)
  • Documentos HTML traduzidos são armazenados como {name}.{lang}.html (por exemplo, docs.es.html)
  • Cada arquivo em cache inclui um hash SHA-256 da fonte — se a fonte em inglês não mudou, a tradução é pulada
  • Exclua o arquivo em cache para forçar a retradução na próxima reinicialização
