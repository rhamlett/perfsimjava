☁️Azure Diagnóstico

Guia para diagnosticar problemas de desempenho com ferramentas Azure

Visão geral

Este guia explica como usar Azure ferramentas de diagnóstico para analisar problemas de desempenho simulados por esta aplicação.

🔗 Correlação do ID da Simulação

Cada instância de simulação recebe um ID de Simulação único (GUID) que permite correlação de ponta a ponta entre a interface do painel e Azure Application Insights telemetria.

Encontrando IDs de Simulação

No Painel: Mensagens de início e conclusão de simulação no Registro de Eventos possuem um sublinhado pontilhado sutil indicando que são interativos. Passe o mouse sobre essas mensagens para ver a informação completa ID de simulação em uma dica de ferramenta. Clique para copiar para a sua prancheta.

Em Azure: O mesmo ID de simulação é emitido nos logs do lado do servidor e pode ser encontrado em:

  • Application Insights — Rastreios de busca e eventos personalizados por ID de Simulação
  • Análise de Logs — Logs de consulta usando o ID como filtro
  • App Service Registros — Filtre stdout/stderr pelo GUID

// Find simulation start/end events by Simulation ID
AppEvents
| where Name in ("SimulationStarted", "SimulationEnded")
| where Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
| project TimeGenerated, Name, Properties
| order by TimeGenerated asc
// Find all requests during a simulation time window
let simStart = toscalar(
    AppEvents 
    | where Name == "SimulationStarted" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
let simEnd = toscalar(
    AppEvents 
    | where Name == "SimulationEnded" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| order by TimeGenerated asc
// Find failed requests during a simulation
let simId = "YOUR-SIMULATION-ID-HERE";
let simEvents = AppEvents | where Properties["SimulationId"] == simId;
let simStart = toscalar(simEvents | where Name == "SimulationStarted" | project TimeGenerated);
let simEnd = toscalar(simEvents | where Name == "SimulationEnded" | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| where Success == false
| project TimeGenerated, Name, ResultCode, DurationMs, Url
| order by TimeGenerated asc

Fluxo de Trabalho de Solução de Problemas

  1. Inicie uma simulação a partir do painel
  2. Passe o mouse sobre a mensagem de início no Log de Eventos para copiar o ID da Simulação
  3. Abrir Azure Portal → Application Insights → Logs (ou Análise de Logs)
  4. Consulte logs usando o ID de simulação para ver toda a atividade relacionada do lado do servidor
  5. Correlacione carimbos de tempo entre eventos do painel e métricas de servidor

💡 Dica

O ID de Simulação ajuda a isolar a telemetria ao executar múltiplas simulações simultâneas ou quando o painel é usado por múltiplos usuários.

AppLens Integração

Esta aplicação foi projetada para trabalhar com Azure AppLens enviando sondas de saúde a cada 100ms pelo frontend de Azure carimbo. Essa sondagem de alta frequência garante que a latência aumente e Problemas de disponibilidade são visíveis em AppLens dashboards.

O que AppLens Pode Detectar

  • CPU Estresse: Gráficos de alta utilização CPU , alertas potenciais de redução de velocidade
  • Pressão de Memória:Picos de uso de memória, padrões de potencial OOM
  • Privação de Fios: Aumento da latência de solicitações, fila de solicitações
  • Pool de Conexões: Dumps de threads mostram estado ESPERANDO, erros de timeout
  • Pedidos Fracassados:HTTP picos de erro 5xx, queda na disponibilidade, aumento na taxa de erro
  • Quedas: Instância reinicia, disponibilidade cai

Azure Métricas de Monitoramento

Métricas principais para observar no Azure Monitor ao rodar simulações:

Métricas de Plataforma

  • CPU Percentual:Fique atento a picos durante simulações de estresse CPU
  • Conjunto de Trabalho de Memória: Aumentos durante simulações de pressão de memória
  • HTTP Duração da Fila: Cresce durante a falta de fios
  • Tempo de Resposta: Fique atento ao aumento da latência P95/P99
  • Http 5xx: Aumentos durante solicitações falhadas e simulações de falhas

Métricas de JVM (se o App Insights estiver ativado)

  • jvm_memory_used: Memória heap e não-heap
  • jvm_gc_pause:GC tempos de pausa
  • jvm_threads_live: Contagem ativa de threads

Application Insights

Se Application Insights estiver configurado, você pode usar estes recursos:

Transmissão de Métricas ao Vivo

Assista a métricas em tempo real durante as simulações:

  1. Navegue até seu App Service no Azure Portal
  2. Acesse Application Insights → Live Metrics
  3. Observe CPU, memória e taxas de solicitação em tempo real

Busca de Transações

Encontre pedidos lentos ou fracassados:

  1. Vá para Application Insights → Busca de Transações
  2. Filtre por "Solicitações falhadas" ou "Tempo de resposta do servidor > 5s"
  3. Analise pedidos individuais para ver a divisão de tempo

Mapa de Aplicação

Visualize a saúde do serviço e as dependências:

  1. Vá para Application Insights → Mapa de Aplicação
  2. Procure indicadores vermelhos/amarelos durante as simulações
  3. Verifique se há taxas de falha ou latência aumentada

Diagnosticar e Resolver Problemas

Azure App Service oferece ferramentas de diagnóstico integradas:

Disponibilidade e desempenho

  1. Vá para App Service → Diagnosticar e resolver problemas
  2. Selecione "Disponibilidade e Desempenho"
  3. Verifique "HTTP 5xx Erros" para problemas relacionados a travamentos
  4. Verifique "High CPU" para detectar CPU estresse
  5. Verifique "Memória" para a detecção de pressão de memória

Ferramentas de Diagnóstico

  • CPU Aprofunde: Veja CPU divisão de uso por instância
  • Despejo de Memória: Capturar dumps de heap durante problemas de memória
  • Despejo de Thread: Capturar pilhas de fios durante a fome
  • JFR (Gravador de Voo Java): Aplicação Java de perfil

Análise de Logs / Consultas KQL

Consultas úteis do KQL para analisar efeitos de simulação:

Pedidos de Alta CPU

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where ScStatus >= 500
| summarize Count=count() by bin(TimeGenerated, 1m)
| render timechart

Tempos de resposta lentos

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where TimeTaken > 5000
| project TimeGenerated, CsUriStem, TimeTaken, ScStatus
| order by TimeTaken desc

Padrão de Uso de Memória

AppServicePlatformLogs
| where TimeGenerated > ago(1h)
| where Level == "Informational"
| project TimeGenerated, Message
| order by TimeGenerated desc

Diagnósticos Específicos para Java

Ativer o JMX para Monitoramento Remoto

Adicione estas configurações de app para acesso ao JMX (apenas desenvolvimento):

JAVA_OPTS=-Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9010 \
  -Dcom.sun.management.jmxremote.local.only=false \
  -Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false

Ativar o registro GC

JAVA_OPTS=-Xlog:gc*:file=/home/LogFiles/gc.log:time,level,tags

Despejamentos de pilha em OOM

JAVA_OPTS=-XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/home/LogFiles/heapdump.hprof

Despejos de Thread de Leitura: Exaustão da Piscina de Conexão

Ao diagnosticar problemas de pool de conexão, procure por tópicos em TIMED_WAITING Estado bloqueado na aquisição de recursos:

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)

Exemplo real do HikariCP:

"http-nio-8080-exec-15" TIMED_WAITING
    at com.zaxxer.hikari.pool.HikariPool.getConnection(...)
    at com.zaxxer.hikari.HikariDataSource.getConnection(...)

O que o tópico afirma significar:

  • EXECUTÁVEL — Executar ativamente (CPU trabalho)
  • BLOQUEADO — Aguardando um bloqueio de monitor (bloco sincronizado)
  • ESPERANDO — Aguardando indefinidamente (Object.wait, Thread.join)
  • TIMED_WAITING — Esperar com tempo de espera (comum em tempos de descanso na piscina)

Muitos threads em TIMED_WAITING sobre aquisição de pool = esgotamento de pool de conexão. Aumente o tamanho do pool ou reduza o tempo de espera da consulta.

Melhores Práticas

Comece devagar

Comece com simulações de curta duração (10-30 segundos) e baixa intensidade (2-4 trabalhadores, 100-200MB de memória) para entender o impacto de base antes de ampliar.

Monitore antes de simular

Estabeleça uma linha de base observando métricas por alguns minutos antes Iniciando qualquer simulação. Isso facilita a identificação de mudanças.

Cautela de Produção

Nunca execute simulações de colisão ou testes de estresse de alta intensidade em produção ambientes. Use slots de staging/desenvolvimento para testes.
