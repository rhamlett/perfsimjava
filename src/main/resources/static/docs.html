Performance Problem Simulator - Java 21

📚 Documentation

Complete API reference and guides for PerfSimJava performance simulation tools

Overview

PerfSimJava is an educational tool designed to help Azure support engineers practice diagnosing common Java performance problems. It intentionally generates controllable performance issues that mimic real-world scenarios.

Features

  • CPU Stress - Generate high CPU usage at configurable percentages
  • Memory Pressure - Allocate and retain memory to simulate leaks
  • Thread Starvation - Block the servlet thread pool with synchronous operations
  • Connection Pool - Simulate JDBC connection pool exhaustion
  • Crash Simulation - Trigger unhandled exceptions or OOM conditions

Health Endpoints

GET /health

Returns the application health status.

{
    "status": "healthy",
    "timestamp": "2024-01-01T00:00:00Z",
    "version": "1.0.0",
    "runtime": "Java 21"
}
GET /health/live

Kubernetes liveness probe endpoint. Returns HTTP 200 if the application is alive.

GET /health/ready

Kubernetes readiness probe endpoint. Returns HTTP 200 if the application is ready to serve traffic.

CPU Stress Simulation

POST /api/simulations/cpu/stress

Starts a CPU stress simulation with cryptographic operations.

Request Body:

{
    "workers": 4,        // Number of worker threads (1-32)
    "durationMs": 30000  // Duration in milliseconds
}
DELETE /api/simulations/cpu/stress/{simulationId}

Stops a running CPU stress simulation.

GET /api/simulations/cpu/active

Lists all active CPU stress simulations.

Memory Pressure Simulation

POST /api/simulations/memory/pressure

Starts a memory pressure simulation by allocating heap memory.

Request Body:

{
    "targetMb": 500,     // Target memory allocation in MB
    "durationMs": 30000  // Duration to hold memory
}
DELETE /api/simulations/memory/pressure/{simulationId}

Releases memory from a running simulation.

Thread Pool Starvation Simulation

Note: This is the Java equivalent of "Event Loop Blocking" in Node.js. Since Java uses a thread-per-request model, blocking multiple servlet threads simulates the same symptom of request queueing and latency spikes.
POST /api/simulations/thread/starvation

Starts blocking servlet threads to starve the thread pool.

Request Body:

{
    "blockedThreadCount": 50,  // Number of threads to block (10-200)
    "durationMs": 30000        // Duration to block
}

Connection Pool Exhaustion

Understanding Connection Pools

Database connection pools (like HikariCP, C3P0, Tomcat JDBC) maintain a fixed number of reusable database connections. When all connections are in use, new requests must wait. This is one of the most common performance issues in Java applications.

How This Simulation Works

We use a Semaphore — a Java concurrency primitive that controls access to a limited number of resources. Think of it like a parking lot:

  • Pool Size = Number of parking spaces
  • acquire() = Car takes a space (gets a connection)
  • release() = Car leaves (returns connection to pool)
  • Waiting threads = Cars queued at the gate when lot is full

Semaphore → HikariCP Mapping:

new Semaphore(10) maximumPoolSize=10
tryAcquire(30, SECONDS) connectionTimeout=30000
release() Connection returned to pool
Thread blocked on acquire Thread waiting for available connection
POST /api/simulations/connection-pool

Simulates JDBC connection pool exhaustion. Multiple queries compete for limited connections, causing timeouts.

Request Body:

{
    "poolSize": 10,              // Simulated pool size (like HikariCP)
    "queryDurationSeconds": 30,  // How long each query holds a connection
    "concurrentQueries": 20,     // Number of concurrent queries
    "connectionTimeoutSeconds": 5 // Timeout waiting for connection
}

Diagnostic Value:

  • Thread dumps show threads TIMED_WAITING on Semaphore.tryAcquire
  • Identical pattern to real HikariCP/C3P0 pool exhaustion
  • Latency spikes as servlet threads block waiting for connections
  • Timeout errors when wait exceeds connectionTimeoutSeconds

What You'll See in Thread Dumps

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)
    at com.microsoft.azure.samples.perfsimjava.service.ConnectionPoolService.executeQuery(...)
    ...

In real applications, this would show HikariPool.getConnection() or BasicResourcePool.getResource() instead.

GET /api/simulations/connection-pool/stats

Returns current pool statistics including available connections, active connections, and timeout counts.

DELETE /api/simulations/connection-pool

Stops the connection pool simulation and releases all connections.

Crash Simulation

Warning: These endpoints will crash or terminate the application. Use only for testing diagnostics and recovery scenarios.
POST /api/simulations/crash

Triggers a crash of the specified type.

Request Body:

{
    "type": "FAILFAST"  // FAILFAST, STACKOVERFLOW, EXCEPTION, or OOM
}
POST /api/simulations/crash/failfast

Immediately exits the JVM with System.exit(1).

POST /api/simulations/crash/stackoverflow

Causes a StackOverflowError through infinite recursion.

POST /api/simulations/crash/exception

Throws an unhandled RuntimeException.

POST /api/simulations/crash/oom

Causes an OutOfMemoryError by allocating excessive memory.

Admin Endpoints

GET /api/simulations

Lists all active simulations.

GET /api/admin/status

Returns admin status overview with metrics and simulation count.

GET /api/admin/events

Returns recent event log entries.

Query Parameters:

  • limit - Maximum number of events to return (default: 50)

WebSocket Topics (STOMP)

Connect to WebSocket at /ws using SockJS and STOMP protocol.

Subscribe Topics:

  • /topic/metrics - System metrics (every 250ms)
  • /topic/probe - Probe latency results (every 100ms)
  • /topic/events - Event log entries
  • /topic/simulations - Simulation lifecycle updates

Technology Stack

  • Runtime: Java 21 (Blessed Image)
  • Framework: Spring Boot 3.3
  • WebSocket: STOMP over SockJS
  • Metrics: JMX MBeans (OperatingSystemMXBean, MemoryMXBean, ThreadMXBean)
  • CPU Stress: PBKDF2WithHmacSHA512 cryptographic operations
