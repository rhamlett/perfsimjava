Performance Problem Simulator - Java 21

📚 Documentation

Complete API reference and guides for PerfSimJava performance simulation tools

Overview

PerfSimJava is an educational tool designed to help Azure support engineers practice diagnosing common Java performance problems. It intentionally generates controllable performance issues that mimic real-world scenarios.

Features

  • CPU Stress - Generate high CPU usage at configurable percentages
  • Memory Pressure - Allocate and retain memory to simulate leaks
  • Thread Starvation - Block the servlet thread pool with synchronous operations
  • Connection Pool - Simulate JDBC connection pool exhaustion
  • Failed Requests - Generate HTTP 5xx errors visible in AppLens and App Insights
  • Crash Simulation - Trigger unhandled exceptions or OOM conditions

Metrics

The dashboard displays real-time system metrics streamed via WebSocket. Metrics include:

  • CPU — Usage percentage, processor count, system load average
  • Memory — Heap used/max, heap percentage, non-heap memory
  • Threads — Active count, peak count, total threads started
  • GC — Collection count and total pause time

These metrics are collected from JMX MBeans and update every 250ms on the dashboard.

CPU Stress Simulation

How It Works

The CPU stress simulation creates worker threads that perform PBKDF2WithHmacSHA512 cryptographic operations—computationally expensive work that cannot be optimized away by the JIT compiler.

Understanding the Simulation

Each worker thread runs in a tight loop performing password hashing operations. This mimics real-world scenarios like:

  • Inefficient algorithms — O(n²) loops or regex backtracking
  • Missing caches — Recalculating expensive operations repeatedly
  • Crypto-mining malware — Unauthorized CPU consumption
  • Unoptimized queries — CPU-bound data processing

Configuration Options

  • Duration (seconds) — How long the stress runs before automatically stopping.
  • Intensity — Choose High or Moderate to control CPU consumption level.

What You'll See in Diagnostics

  • Thread dumps: Threads in RUNNABLE state inside PBKDF2Core or SecretKeyFactory
  • CPU Profiler: High CPU samples in cryptographic classes
  • App Service Metrics: CPU percentage spike during simulation

Dashboard Controls

Use the CPU Stress panel on the dashboard to start/stop simulations. Select intensity level and duration, then click Trigger CPU Stress.

Memory Pressure Simulation

How It Works

The memory simulation allocates large byte arrays that are held on the heap until explicitly released, preventing garbage collection from reclaiming the memory.

Understanding Memory Leaks

In real applications, memory leaks occur when objects remain reachable but are no longer needed. Common causes include:

  • Static collections — Adding to a static List or Map without removing
  • Event listeners — Registering listeners that are never unregistered
  • Caches without eviction — Unbounded caches that grow indefinitely
  • ThreadLocal variables — Values held in pooled threads
  • Session data — Large objects stored in HTTP sessions

Configuration Options

  • Size (MB) — Amount of heap memory to allocate per click. Multiple allocations stack.

What You'll See in Diagnostics

  • GC Frequency: Increased GC activity as heap fills up
  • Heap Dumps: Large byte[] arrays retained by the simulation service
  • Memory Metrics: Heap usage climbing toward the configured target
  • GC Pauses: Longer GC times as the heap approaches capacity

Dashboard Controls

Use the Memory panel on the dashboard to allocate memory and watch heap usage grow in real-time. Click Release to free all allocated memory on demand.

Thread Pool Starvation Simulation

Note: This is the Java equivalent of "Event Loop Blocking" in Node.js. Since Java uses a thread-per-request model, blocking multiple servlet threads simulates the same symptom of request queueing and latency spikes.

Understanding Duration and Thread Count

The simulation spawns internal HTTP requests that each block a servlet thread. Here's how the timing works:

  • Duration per request: Each blocking request runs for the specified duration (e.g., 10s)
  • Tomcat thread pool: Default max ~200 threads
  • Wave behavior: If you spawn more threads than the pool size, excess requests queue in Tomcat's HTTP queue

Example Timeline (220 threads, 10s duration):

Time What Happens
0-10s First 200 requests grab threads, start blocking. 20 requests waiting in queue.
~10s First wave completes. Queued 20 requests now get threads.
~20s Second wave completes. Simulation ends.

Formula: Total time ≈ durationSeconds × ⌈threadCount / 200⌉

Configuration Options

  • Blocked Threads — Number of blocking requests to spawn
  • Duration (seconds) — How long each request blocks its thread

Recommended Settings:

  • Quick test: 150 threads, 10s (single wave, ~10s total)
  • Moderate impact: 200 threads, 15s (saturates pool, ~15s total)
  • Extended test: 400 threads, 10s (two waves, ~20s total)

What You'll See in Diagnostics

  • Thread dumps: Many threads in TIMED_WAITING state
  • Latency spikes: New requests queue behind blocked threads
  • Dashboard: Active thread count climbs rapidly

Connection Pool Exhaustion

Understanding Connection Pools

Database connection pools (like HikariCP, C3P0, Tomcat JDBC) maintain a fixed number of reusable database connections. When all connections are in use, new requests must wait. This is one of the most common performance issues in Java applications.

How This Simulation Works

We use a Semaphore — a Java concurrency primitive that controls access to a limited number of resources. Think of it like a parking lot:

  • Pool Size = Number of parking spaces
  • acquire() = Car takes a space (gets a connection)
  • release() = Car leaves (returns connection to pool)
  • Waiting threads = Cars queued at the gate when lot is full

Semaphore → HikariCP Mapping:

new Semaphore(10) maximumPoolSize=10
tryAcquire(30, SECONDS) connectionTimeout=30000
release() Connection returned to pool
Thread blocked on acquire Thread waiting for available connection

Configuration Options

Adjustable via the dashboard:

  • Pool Size — Number of simulated connections available
  • Query Duration (seconds) — How long each \"query\" holds a connection
  • Concurrent Queries — Number of simultaneous queries to attempt
  • Connection Timeout (seconds) — How long to wait before timing out

What You'll See in Thread Dumps

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)
    at com.microsoft.azure.samples.perfsimjava.service.ConnectionPoolService.executeQuery(...)
    ...

In real applications, this would show HikariPool.getConnection() or BasicResourcePool.getResource() instead.

Diagnostic Indicators

  • Thread dumps show threads TIMED_WAITING on Semaphore.tryAcquire
  • Latency spikes as servlet threads block waiting for connections
  • Timeout errors when wait exceeds the configured timeout
  • Dashboard shows real-time pool utilization and timeout counts

Failed Requests Simulation

How It Works

The Failed Requests simulation generates HTTP 5xx errors by making internal requests to the load test endpoint with 100% error probability. Each request produces a visible server error that appears in Azure diagnostics.

Understanding HTTP 5xx Errors

HTTP 5xx errors indicate server-side failures. This simulation helps you practice identifying and diagnosing error patterns using Azure tools:

  • AppLens: HTTP 5xx errors appear on the availability timeline and in error reports
  • Application Insights: Failed requests are tracked with full exception details
  • Azure Monitor: Http5xx metric increases, triggering any configured alerts
  • Log Analytics: Error details available via KQL queries

Configuration Options

  • Number of Requests — How many failed requests to generate (1-1000, default: 10)

What You'll See in Diagnostics

  • AppLens: HTTP 5xx error spike on timeline, availability drop
  • Application Insights: Failed requests with exception types like TimeoutException, IOException
  • Azure Monitor: Http5xx metric increase
  • Request Latency: Each request takes ~2+ seconds to execute before failing

API Endpoint

POST /api/simulations/failed-requests

Triggers a batch of HTTP 5xx error requests.

Request Body:

{
    "numberOfRequests": 10
}

Response:

{
    "simulationId": "abc123",
    "type": "FAILED_REQUESTS",
    "numberOfRequests": 10,
    "status": "RUNNING",
    "message": "Generating 10 failed HTTP requests"
}

Dashboard Controls

Use the Failed Requests panel on the dashboard to generate errors. Enter the number of requests and click Generate Errors. The simulation executes quickly and produces HTTP 5xx responses visible in Azure diagnostics tools.

Crash Simulation

Warning: These simulations will crash or terminate the application. Use only for testing diagnostics and recovery scenarios in App Service.

Available Crash Types

Select a crash type from the dashboard to test different failure modes:

🛑 Fail Fast (System.exit)

Immediately terminates the JVM with System.exit(1). The process exits without running shutdown hooks or finalizers. In App Service, this triggers an immediate restart.

📉 Stack Overflow

Triggers a StackOverflowError through infinite recursion. This simulates bugs like circular method calls or unbounded recursion. The stack trace will show repeated calls to the same method.

⚠️ Unhandled Exception

Throws an unhandled RuntimeException from a request handler. Tests how your application handles unexpected errors and whether exception handling middleware is working correctly.

💥 Out of Memory (OOM)

Rapidly allocates memory until the JVM throws an OutOfMemoryError. This is useful for testing:

  • App Service auto-restart behavior on OOM
  • Memory alerting and monitoring
  • Heap dump collection configuration

Load Testing

Designed for Load Testing Tools

This endpoint is optimized for use with Azure Load Testing, Apache JMeter, k6, or similar tools. It performs lightweight work that compounds under high concurrency to demonstrate timeout behavior.

How It Works

  1. Memory Allocation: Allocates a buffer (default 20MB) and touches each page to ensure real memory commitment
  2. Degradation Delay: Calculates total delay based on concurrent requests:
    totalDelay = baselineDelayMs + max(0, concurrent - softLimit) × degradationFactor
  3. Sustained Work Loop: Interleaves CPU spin work, memory touches, and 50ms sleeps
  4. Exception Injection: After errorAfter seconds of processing (default: 120), each cycle has an errorPercent chance (default: 20%) of throwing a random exception. Errors are checked after thread blocking delays to ensure chaotic timing.

Under Load Behavior

As concurrent requests increase:

  • Response times grow linearly beyond the soft limit
  • Memory pressure builds as more requests hold buffers simultaneously
  • After errorAfter seconds of processing (default: 120), random exceptions start appearing with errorPercent probability per check (default: 20%)
  • At high enough load, requests may hit the Azure App Service 230-second frontend timeout
GET /api/loadtest

Executes a load test request with configurable CPU work and memory usage.

Query Parameters:

Parameter Default Range Description
workIterations 200 1-10,000 CPU work intensity per cycle (ms = iterations/100)
bufferSizeKb 20,000 100-500,000 Memory buffer held per request (KB)
baselineDelayMs 500 100-60,000 Minimum request duration (ms)
softLimit 25 1-1,000 Concurrent requests before degradation begins
degradationFactor 500 0-10,000 Additional delay (ms) per request over soft limit
errorAfter 120 0+ Seconds before random errors may occur (0 disables)
errorPercent 20 0-100 Percentage chance of error after threshold (0 disables)
Note: Actual response times will vary based on your Azure App Service tier, current load, and other factors. Use Azure Load Testing to establish baseline performance for your specific environment. These example scenarios, and the defaults, are for a Premium0V3 worker. Any other SKU or worker size will need individual tuning.

Exception Types Injected

After errorAfter seconds of processing (default: 120), the following exceptions may be thrown with errorPercent probability per check (default: 20%):

  • IllegalStateException - Invalid operation state
  • NullPointerException - Null reference
  • TimeoutException - Operation timeout
  • IOException - I/O error
  • ArithmeticException - Divide by zero
  • IllegalArgumentException - Invalid argument
  • IndexOutOfBoundsException - Index out of range
  • UnsupportedOperationException - Operation not supported
  • SecurityException - Security violation
  • ClassCastException - Invalid cast

Admin Endpoints

These endpoints power the dashboard and provide programmatic access to simulation status:

  • GET /api/simulations — Lists all active simulations
  • GET /api/admin/status — Overview with metrics and simulation count
  • GET /api/admin/events — Recent event log entries

WebSocket Topics (STOMP)

Connect to WebSocket at /ws using SockJS and STOMP protocol.

Subscribe Topics:

  • /topic/metrics - System metrics (every 250ms)
  • /topic/probe - Probe latency results (every 100ms)
  • /topic/events - Event log entries
  • /topic/simulations - Simulation lifecycle updates

Technology Stack

  • Runtime: Java 21 (Blessed Image)
  • Framework: Spring Boot 3.3
  • WebSocket: STOMP over SockJS
  • Metrics: JMX MBeans (OperatingSystemMXBean, MemoryMXBean, ThreadMXBean)
  • CPU Stress: PBKDF2WithHmacSHA512 cryptographic operations

Environment Variables

The following environment variables can be configured to customize application behavior:

Variable Description
PAGE_FOOTER Custom HTML footer text displayed at the bottom of the dashboard. Supports HTML links.
HEALTH_PROBE_RATE Latency probe interval in milliseconds. Default: 200ms. Minimum: 100ms.
IDLE_TIMEOUT_MINUTES Idle timeout in minutes. When app is idle, health probes stop to reduce traffic. Default: 20. Set to 0 to disable.

HEALTH_PROBE_RATE

The HEALTH_PROBE_RATE environment variable controls how frequently the server sends health probe requests to measure request latency. Lower values provide more granular latency data but increase CPU overhead.

  • Default: 200ms (5 probes/sec)
  • Minimum: 100ms (values below this are automatically clamped)
  • Chart updates: The latency chart continues to update at 100ms regardless of probe rate, using interpolation

Setting via Azure CLI:

az webapp config appsettings set \
    --resource-group rg-perfsimjava \
    --name perfsimjava \
    --settings HEALTH_PROBE_RATE=400

Setting Locally:

export HEALTH_PROBE_RATE=400

PAGE_FOOTER

The PAGE_FOOTER environment variable allows you to customize the footer credits displayed on the dashboard. This is useful for attributing tools, teams, or linking to relevant resources.

Example Value:

Created by <a href="https://speckit.org/" target="_blank">SpecKit</a> and <a href="https://github.com/copilot" target="_blank">Github Copilot</a>

Setting via Azure CLI:

az webapp config appsettings set \
    --resource-group rg-perfsimjava \
    --name perfsimjava \
    --settings PAGE_FOOTER='Created by <a href="https://speckit.org/" target="_blank">SpecKit</a> and <a href="https://github.com/copilot" target="_blank">Github Copilot</a>'

Setting Locally:

export PAGE_FOOTER='Created by <a href="https://speckit.org/" target="_blank">SpecKit</a> and <a href="https://github.com/copilot" target="_blank">Github Copilot</a>'

The footer is retrieved via the /api/health/footer endpoint and rendered in the dashboard's footer section. If PAGE_FOOTER is not set, the footer credits section is hidden.

IDLE_TIMEOUT_MINUTES

The IDLE_TIMEOUT_MINUTES environment variable controls how long the application can remain idle before health probes are paused. This reduces unnecessary traffic to AppLens and Application Insights when the app is not being actively used.

  • Default: 20 minutes
  • Minimum: 1 minute (set to 0 to disable idle timeout entirely)
  • Wake-up: The app automatically wakes when a page is loaded or a load test request is received

Behavior When Idle:

  • Local health probes stop being sent
  • Frontend probes (Azure AppLens visibility) stop being sent
  • Event log shows "Application going idle, no health probes being sent. There will be gaps in diagnostics and logs."

Behavior When Waking:

  • Page load or load test activity resets the idle timer
  • Event log shows "App waking up from idle state. There may be gaps in diagnostics and logs."
  • Health probes resume immediately

Setting via Azure CLI:

az webapp config appsettings set \
    --resource-group rg-perfsimjava \
    --name perfsimjava \
    --settings IDLE_TIMEOUT_MINUTES=30

Setting Locally:

export IDLE_TIMEOUT_MINUTES=30

Disabling Idle Timeout:

export IDLE_TIMEOUT_MINUTES=0
