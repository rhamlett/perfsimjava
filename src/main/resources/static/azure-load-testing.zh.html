📈 Azure 负载测试指南

为 Azure 负载测试集成设计的负载测试端点

🔬 概述

性能问题模拟器包含专用的负载测试终端 设计用于 Azure 载荷测试。该端点模拟真实感 应用行为在负载下会优雅地下降。

该 /api/loadtest 端点设计目的是：

  • 执行持续 CPU 工作（交错的SHA256周期，每线程 CPU 约50%）
  • 在整个请求期间保持内存缓冲区（产生可见的内存压力）
  • 随着并发请求增加（软限制模式），性能下降
  • 在可配置阈值（默认：120秒，概率20%）后抛出随机异常。
  • 最终在极高负载下触发 Azure230秒的超时

⚙️ 设置 Azure 负载测试

  1. 在 Azure 门户中，创建一个 Azure 负载测试资源
  2. 创建一个新测试，并使用以下选项之一配置目标URL：

GET 查询参数

直接使用目标网址——无需 JMeter 脚本：

# With defaults
https://your-app.azurewebsites.net/api/loadtest

# Custom parameters
https://your-app.azurewebsites.net/api/loadtest?workIterations=500&bufferSizeKb=10000

# Thread pool only (no CPU work)
https://your-app.azurewebsites.net/api/loadtest?workIterations=0&bufferSizeKb=100

POST 请求体

对于更复杂的场景，可以使用JSON体的POST：

POST /api/loadtest
Content-Type: application/json

{
  "workIterations": 200,
  "bufferSizeKb": 20000,
  "softLimit": 25,
  "degradationFactor": 500,
  "baselineDelayMs": 500,
  "errorAfterSeconds": 120,
  "errorPercent": 20
}
  1. 配置负载模式（增加、稳态、下降）
  2. 设置 Azure 监控集成以关联指标

📋 查询参数参考

每个参数独立控制特定资源：

参数 默认 目标资源 描述
workIterations 200 CPU 每个 CPU 工作周期的 SHA256 哈希迭代。控制持续 CPU 使用率（每线程约50%）。
bufferSizeKb 20000 记忆 内存以KB为单位，整个请求持续时间内保持（默认为20 MB）。会造成持续的记忆压力。
baselineDelayMs 500 线程池 最小请求时长（毫秒）。 CPU 工作和睡眠交替进行。
softLimit 25 线程池 降级前并发请求。低 = 更快的疲劳。
degradationFactor 500 线程池 每个请求在softLimit上额外延迟（毫秒）。
errorAfter 120 混沌 在出现随机错误前几秒钟。设置为0以禁用。
errorPercent 20 混沌 阈值后每个检查间隔随机出现错误的概率（0-100）。

📊 理解软极限

软极限形成一个退化曲线，响应时间随 并发请求超过阈值。降解公式为： 

additionalDelay = max(0, concurrent - softLimit) × degradationFactor

注： 实际响应时间会根据你当前的 Azure App Service 等级而异 负荷，以及其他因素。利用 Azure 负载测试来建立基线性能 针对你具体的环境。默认参数是为 Premium0V3 工作者调校的。 其他的 SKU 或工种尺寸都需要单独调校。

降解模式示例

默认设置下 （softLimit=25, degradationFactor=500):

并行请求 额外延迟 预期响应时间
10 0毫秒 ~500毫秒（仅基线）
25 0毫秒 ~500毫秒（软限制）
50 12,500毫秒 ~13
100 37,500毫秒 ~38

💥 错误注入

负载测试端点可以注入随机异常以模拟真实情况 应用程序失败。这由两个参数控制：

  • errorAfter （默认：120）- 错误开始前几秒
  • errorPercent （默认：20）- 达到阈值后出现错误的概率

例外类型

随机例外从现实的 Java 异常池中选取：

例外类型 示例消息
IllegalStateException 由于对象当前状态，操作不成立
NullPointerException 对象引用未设置为对象的实例
TimeoutException 行动已超时
IOException 处理过程中发生了I/O错误
ArithmeticException 尝试除以零
IllegalArgumentException 提供的无效论证
IndexOutOfBoundsException 指数超出范围
UnsupportedOperationException 操作不支持
SecurityException 检测到安全违规
ClassCastException 指定的掷法无效

禁用错误注入

# Disable errors entirely
/api/loadtest?errorAfter=0

# Or set errorPercent to 0
/api/loadtest?errorPercent=0

🔍 负荷测试结果诊断

1. Application Insights 积分

  • 前往 Application Insights >表演
  • 按操作名称进行筛选 GET /api/loadtest
  • 观察响应时间百分位数（第50页，第95页，第99页）
  • 检查可配置的随机错误阈值（默认：120秒）的失败率

2. Azure 监测指标

  • 请求 - 总请求数和速率
  • 响应时间 - 平均和百分位延迟
  • HTTP 服务器错误 - 随机异常导致的5xx错误
  • CPU 百分比 - 应随负载增加
  • 记忆工作集 - 应随bufferSizeKb增加

3. 负载测试统计端点

测试期间查询统计端点：

GET /api/loadtest/stats

{
  "currentConcurrentRequests": 127,
  "peakConcurrentRequests": 156,
  "totalRequests": 45230,
  "successfulRequests": 45207,
  "failedRequests": 23,
  "errorRate": 0.05,
  "averageResponseTimeMs": 847.5,
  "minResponseTimeMs": 512,
  "maxResponseTimeMs": 3421,
  "requestsPerSecond": 42.3
}

📤 响应格式

每次成功请求返回：

{
  "requestId": "a1b2c3d4",
  "elapsedMs": 1247,
  "concurrentAtStart": 42,
  "calculatedDelayMs": 8500,
  "workIterationsCompleted": 200,
  "bufferSizeKb": 20000,
  "workCompleted": true,
  "message": "Load test completed in 1247ms"
}

响应场

场地 描述
requestId 该请求的唯一标识符（用于关联）
elapsedMs 总请求时长（毫秒）
concurrentAtStart 请求开始时并发请求数量
calculatedDelayMs 总延迟（基线 + 降级）
workIterationsCompleted 完成的SHA256哈希迭代次数
bufferSizeKb 为该请求分配的内存缓冲区大小（KB）
workCompleted 所有工作是否成功完成
message 人类可读的完成信息

✅ 最佳实践

DO：

  • ✅ 从默认参数开始建立基线
  • ✅ 在负载测试中监控 Azure 指标
  • ✅ 用 /api/loadtest/stats 端点来跟踪并发
  • ✅ 逐渐增加负载以找到断裂点
  • ✅ 将载荷测试结果与Application Insights相关
  • ✅ 用真实的负载模式测试（加量、稳态、减速）

不要这样做：

  • ❌ 从极端参数开始
  • ❌ 使用大缓冲区大小Kb时忽略内存度量
  • ❌ 如果你想看到真实的失败，可以运行 errorAfter=0 的扩展测试
  • ❌ 假设一个 SKU 的结果适用于另一个
