一个教育 Azure App Service 应用，故意制造性能问题以供学习和演示。

⚠️ 警告 —— 该应用故意制造性能问题！
  • 🔥 CPU 压力 — 生成运行加密操作的工线程以消耗 CPU 核心
  • 📊 记忆压力 — 分配并保留大字节数组以增加堆使用率
  • 🟣 线条饥饿 — 块 servlet 线程进行同步操作

CPU 应力模拟

工作原理

CPU应力模拟生成执行以下工作的线程PBKDF2WithHmacSHA512 加密操作——计算量高的工作，无法通过JIT编译器优化消除。

理解模拟

每个工作线程都以紧密循环运行，执行密码哈希操作。这模拟了现实世界的场景，比如：

  • 低效算法 — O（n²） 循环或正则表达式回溯
  • 缺失的缓存 —— 反复重新计算昂贵的操作
  • 加密挖矿恶意软件 — 未经授权 CPU 消费
  • 未优化查询 — CPU-bound 数据处理

配置选项

  • 持续时间（秒） ——应力持续多久后自动停止。
  • 强度 ——选择 高 或 中等 用来控制消费 CPU 。

你在诊断中会看到的内容

  • 帖子转储： 线程 RUNNABLE 内部状态 PBKDF2Core 或 SecretKeyFactory
  • CPU 画像师： 密码学类中的高 CPU 样本
  • App Service 指标：CPU模拟时百分比峰值

仪表盘控制

使用该 CPU 压力 仪表盘上的面板用于启动/停止模拟。选择强度等级和持续时间，然后点击 压力 CPU 诱因.

内存压力仿真

工作原理

内存仿真分配大字节数组，这些数组会被保留在堆上，直到显式释放，以防止垃圾回收回收内存。

理解内存泄漏

在实际应用中，内存泄漏发生在对象仍然可达但不再需要时。常见原因包括：

  • 静态集合 —— 在静态中添加 List 或 Map 无需移除
  • 活动听众 — 注册从未未未登记的听众
  • 无淘汰的缓存 ——无限增长的无上限缓存
  • ThreadLocal 变量 — 集合线程中持有的值
  • 会话数据 — 存储在 HTTP 会话中的大型对象

配置选项

  • 尺寸（MB） — 每点击分配堆内存量。多重配置叠加。

你在诊断中会看到的内容

  • GC 频率： 堆积物满载时 GC 活动增加
  • 堆卸： 大型 byte[] 由仿真服务保留的阵列
  • 记忆指标： 堆使用率向配置目标攀升
  • GC 停顿： 随着堆接近容量， GC 时间会变长

仪表盘控制

使用该 记忆 仪表盘上的面板用于分配内存，实时监控堆使用量增长。咔哒 发行 按需释放所有分配的内存。

线程池饥饿模拟

注： 这就是 Java 版的 Node.js“事件循环阻断”。 由于 Java 采用线程逐请求模型，阻挡多个 servlet 线程会模拟 同样的症状是请求队列和延迟激增。

理解时长与线数

仿真会生成内部 HTTP 请求，要求每个请求阻塞一个 servlet 线程。时间安排如下：

  • 每次请求的持续时间： 每个阻塞请求运行时间为指定的持续时间（例如10秒）
  • Tomcat 线池： 默认最大~200个线程
  • 波动行为： 如果你生成的线程多于池大小，超额请求会排队到 Tomcat 的 HTTP 队列

示例时间线（220个线程，10秒）：

时间 发生了什么
0-10秒 前200个请求抓取线程，开始拉黑。有20个请求在队列中等待。
~10 第一波完成。排队的20个请求现在都被激活了。
~20多 第二波完成。模拟结束。

公式： 总时≈ durationSeconds × ⌈threadCount / 200⌉

配置选项

  • 阻塞的讨论串 — 阻断请求生成次数
  • 持续时间（秒） — 每个请求阻塞其线程的时间

推荐设置：

  • 快速测试： 150线，10秒（单线，总共~10秒）
  • 中等影响： 200个线程，15秒（饱和池子，总共~15秒）
  • 扩展测试： 400个线程，10个线（两个波，总共~20个）

你在诊断中会看到的内容

  • 帖子转储： 许多讨论串 TIMED_WAITING 州
  • 延迟峰值： 新请求排队在被阻塞的线程后面
  • 仪表盘： 主动线数迅速攀升

连接池耗尽

理解连接池

数据库连接池（如 HikariCP、C3P0、Tomcat JDBC）维护固定数量的可重用数据库连接。当所有连接都已使用时，新的请求必须等待。这是 Java 应用中最常见的性能问题之一。

该模拟的工作原理

我们使用 臂板 —— 一个控制有限资源访问的 Java 并发原语。可以把它想象成一个停车场：

  • 泳池规模 = 停车位数
  • acquire（） = Car 占空格（获得连接）
  • release（） = 车辆离开（返回连接池）
  • 等待线程 = 停车场满时在门口排队的车辆

信号量→HikariCP映射：

new Semaphore(10) maximumPoolSize=10
tryAcquire(30, SECONDS) connectionTimeout=30000
release() 连接恢复到台球
获取时线程被阻塞 线程等待可用连接

配置选项

通过仪表盘调节：

  • 泳池规模 — 可用的模拟连接数量
  • 查询时长（秒） — 每个“查询”保持连接的时间
  • 并发查询 — 可尝试同时查询次数
  • 连接超时（秒） — 等多久才会超时

你在帖子转储中看到的内容

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)
    at com.microsoft.azure.samples.perfsimjava.service.ConnectionPoolService.executeQuery(...)
    ...

在实际应用中，这一点会被证明 HikariPool.getConnection() 或 BasicResourcePool.getResource() 反而。

诊断指标

  • 线程转储显示线程 TIMED_WAITING 关于 Semaphore.tryAcquire
  • 当servlet线程阻塞连接等待时，延迟激增
  • 当等待超过配置的超时值时，会出现超时错误
  • 仪表盘显示实时池使用情况和超时计数

失败请求模拟

工作原理

失败请求模拟通过向负载测试端点发出100%错误概率的内部请求，产生 HTTP 5xx个错误。每个请求都会产生一个可见的服务器错误， Azure 诊断中会出现。

理解 HTTP 5xx错误

HTTP 5xx错误表示服务器端故障。该模拟帮助你练习识别和诊断错误模式，使用 Azure 工具：

  • AppLens：HTTP 5xx 错误会出现在可用性时间线和错误报告中
  • Application Insights： 失败请求会被跟踪并附带完整的例外详情
  • Azure 监控： Http5xx 指标增加，触发任何已配置的警报
  • 日志分析： 通过KQL查询获取错误详情

配置选项

  • 请求次数 — 产生失败请求次数（1-1000，默认10）

你在诊断中会看到的内容

  • AppLens：HTTP 时间线上5xx次错误激增，供应量下降
  • Application Insights： 带有异常类型的失败请求，如 TimeoutException、IOException
  • Azure 监控： Http5xx 度规提升
  • 请求延迟： 每个请求执行需~2+秒后才失败

API 端点

POST /api/simulations/failed-requests

触发 HTTP 5xx错误请求。

请求正文：

{
    "numberOfRequests": 10
}

回复：

{
    "simulationId": "abc123",
    "type": "FAILED_REQUESTS",
    "numberOfRequests": 10,
    "status": "RUNNING",
    "message": "Generating 10 failed HTTP requests"
}

撞车模拟

警告： 这些模拟会导致应用程序崩溃或终止。 仅用于测试诊断和恢复场景 App Service。

可用的撞击类型

在仪表盘中选择一种崩溃类型以测试不同的故障模式：

🛑 Fail Fast （System.exit）

立即终止JVM，用 System.exit(1).进程退出时无需运行关闭钩子或终结子。在 App Service中，这会触发立即重启。

📉 堆栈溢出

触发 a StackOverflowError 通过无限递归。这模拟了循环方法调用或无界递归等漏洞。栈追踪会显示对同一方法的多次调用。

⚠️ 未处理异常

扔出一个未被处理的 RuntimeException 来自请求处理员。测试你的应用如何处理意外错误，以及异常处理中间件是否正常工作。

💥 记忆之外（OOM）

快速分配内存，直到JVM抛出 OutOfMemoryError.这对测试很有用：

  • App Service OOM 的自动重启行为
  • 记忆提醒与监控
  • 堆转储收集配置

可选配置

你可以用 Azure App Service 环境变量自定义应用行为。

健康探针率

控制服务器发送健康探针的频率以测量请求延迟。所有探针都经过 Azure 前端，以捕捉真实的端到端延迟。

环境变量

变量名称 描述 默认
HEALTH_PROBE_RATE 探测间隔以毫秒计。至少100毫秒。 200

通过 Azure CLI设置

# Slow down probes if CLR profiler shows overlapping requests
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings HEALTH_PROBE_RATE=400

闲置暂停

当应用程序处于空闲状态（无仪表盘连接或负载测试请求）时，健康探针会自动暂停，以减少不必要的网络流量 Azure前端和 Application Insights 遥测数据。

环境变量

变量名称 描述 默认
IDLE_TIMEOUT_MINUTES 暂停健康探针前的几分钟不活动。当仪表盘打开或收到任何请求时，活动会自动恢复。 20

通过 Azure CLI设置

# Extend idle timeout to 30 minutes
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings IDLE_TIMEOUT_MINUTES=30

自定义页面页脚

设置一个自定义页脚消息，显示在所有页面上。页脚支持 HTML，允许你包含链接。

环境变量

变量名称 描述
PAGE_FOOTER 页脚第二行的HTML内容。如果没有设置，只显示应用描述和构建信息。

示例价值

Created by <a href="https://yoursite.com">Your Team</a> for training purposes

通过 Azure CLI设置

# Set the footer via Azure CLI
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings 'PAGE_FOOTER=Created by <a href="https://yoursite.com">Your Team</a> for training purposes'

通过 Azure 门户设定

  1. 在Azure门户中导航到你的App Service
  2. 前往 背景设定 → 环境变量
  3. 咔哒 + 加法
  4. 套装名称： PAGE_FOOTER
  5. 设置值：你的HTML页脚内容
  6. 咔哒 申请，则 确认

建筑

该应用程序作为 Spring Boot 3.3 应用运行，内置 Tomcat、STOMP over WebSocket 实现实时指标，并支持内存状态。专用探测服务通过前端探测应用来测量请求延迟 Azure。

主要组成部分

  • 弹簧靴应用 — 嵌入式Tomcat服务器，配备REST控制器和 WebSocket 支持。
  • 探测服务— 后台调度任务，通过通过Azure前端发送HTTP探针来测量请求延迟
  • 仿真服务 — CPU 应力、内存压力和线程阻塞模拟在专用线程池中运行，以避免使servlet线程枯竭
  • WebSocket 经纪人 — 通过SockJS进行STOMP消息传递，用于实时仪表盘更新（指标、事件、仿真状态）

🌐 语言选择

仪表盘界面可以用以下支持的任何语言显示 Azure 认知服务翻译器.转换只需在应用启动时执行一次并缓存——运行时翻译开销为零。

工作原理

  1. 设置 UI_LANGUAGE 环境变量 到ISO 639-1语言代码（例如， es, fr, ja, zh-Hans)
  2. 提供 Azure 翻译员资质 通过环境变量
  3. 启动时，应用会翻译所有 UI 字符串（en.json → {lang}.json）以及HTML文档页面
  4. 翻译文件会缓存源的SHA-256哈希值——只有当源代码发生变化时才会重新翻译

所需环境变量

变量 描述 默认
UI_LANGUAGE 目标语言代码 en （无翻译）
TRANSLATOR_API_KEY Azure 译 API 键 —
TRANSLATOR_ENDPOINT 译出服务端点 https://api.cognitive.microsofttranslator.com
TRANSLATOR_REGION Azure 翻译器资源的区域 eastus

Azure App Service 配置

在 Azure 门户，前往你的 App Service → 配置 → 应用设置 并添加：

UI_LANGUAGE=es
TRANSLATOR_API_KEY=your-key-here
TRANSLATOR_REGION=eastus

受保护条款

技术术语列表 locales/no-translate.json （例如，“Azure App Service”、“CPU”、“JVM”、“STOMP”）会自动包裹在 <span class="notranslate"> 在翻译前加上标签，确保无论目标语言为何，都保持在英语中。

缓存行为

  • 翻译过的局部文件存储为 locales/{lang}.json （例如， locales/es.json)
  • 翻译后的HTML文档存储为 {name}.{lang}.html （例如， docs.es.html)
  • 每个缓存文件都包含源代码的SHA-256哈希值——如果英文源码未变，则跳过翻译
  • 删除缓存文件以强制下次重启时重新翻译
