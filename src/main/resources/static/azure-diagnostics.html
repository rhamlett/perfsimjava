☁️ Azure Diagnostics

Guide to diagnosing performance issues with Azure tools

Overview

This guide explains how to use Azure diagnostic tools to analyze performance issues simulated by this application.

AppLens Integration

This application is designed to work with Azure AppLens by sending health probes every 100ms through the Azure stamp frontend. This high-frequency probing ensures that latency spikes and availability issues are visible in AppLens dashboards.

What AppLens Can Detect

  • CPU Stress: High CPU utilization graphs, potential throttling alerts
  • Memory Pressure: Memory usage spikes, potential OOM patterns
  • Thread Starvation: Increased request latency, request queuing
  • Connection Pool: Thread dumps show WAITING state, timeout errors
  • Failed Requests: HTTP 5xx error spikes, availability drops, error rate increases
  • Crashes: Instance restarts, availability drops

Azure Monitor Metrics

Key metrics to watch in Azure Monitor when running simulations:

Platform Metrics

  • CPU Percentage: Watch for spikes during CPU stress simulations
  • Memory Working Set: Increases during memory pressure simulations
  • HTTP Queue Length: Grows during thread starvation
  • Response Time: Watch for P95/P99 latency increases
  • Http 5xx: Increases during failed requests and crash simulations

JVM Metrics (if App Insights enabled)

  • jvm_memory_used: Heap and non-heap memory
  • jvm_gc_pause: GC pause times
  • jvm_threads_live: Active thread count

Application Insights

If Application Insights is configured, you can use these features:

Live Metrics Stream

Watch real-time metrics during simulations:

  1. Navigate to your App Service in Azure Portal
  2. Go to Application Insights → Live Metrics
  3. Observe CPU, memory, and request rates in real-time

Transaction Search

Find slow or failed requests:

  1. Go to Application Insights → Transaction Search
  2. Filter by "Failed requests" or "Server response time > 5s"
  3. Drill into individual requests to see timing breakdown

Application Map

Visualize service health and dependencies:

  1. Go to Application Insights → Application Map
  2. Look for red/yellow indicators during simulations
  3. Check for increased failure rates or latency

Diagnose and Solve Problems

Azure App Service provides built-in diagnostic tools:

Availability and Performance

  1. Go to App Service → Diagnose and solve problems
  2. Select "Availability and Performance"
  3. Check "HTTP 5xx Errors" for crash-related issues
  4. Check "High CPU" for CPU stress detection
  5. Check "Memory" for memory pressure detection

Diagnostic Tools

  • CPU Drill Down: See CPU usage breakdown by instance
  • Memory Dump: Capture heap dumps during memory issues
  • Thread Dump: Capture thread stacks during starvation
  • JFR (Java Flight Recorder): Profile Java application

Log Analytics / KQL Queries

Useful KQL queries for analyzing simulation effects:

High CPU Requests

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where ScStatus >= 500
| summarize Count=count() by bin(TimeGenerated, 1m)
| render timechart

Slow Response Times

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where TimeTaken > 5000
| project TimeGenerated, CsUriStem, TimeTaken, ScStatus
| order by TimeTaken desc

Memory Usage Pattern

AppServicePlatformLogs
| where TimeGenerated > ago(1h)
| where Level == "Informational"
| project TimeGenerated, Message
| order by TimeGenerated desc

Java-Specific Diagnostics

Enable JMX for Remote Monitoring

Add these app settings for JMX access (development only):

JAVA_OPTS=-Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9010 \
  -Dcom.sun.management.jmxremote.local.only=false \
  -Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false

Enable GC Logging

JAVA_OPTS=-Xlog:gc*:file=/home/LogFiles/gc.log:time,level,tags

Heap Dumps on OOM

JAVA_OPTS=-XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/home/LogFiles/heapdump.hprof

Reading Thread Dumps: Connection Pool Exhaustion

When diagnosing connection pool issues, look for threads in TIMED_WAITING state blocked on resource acquisition:

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)

Real HikariCP example:

"http-nio-8080-exec-15" TIMED_WAITING
    at com.zaxxer.hikari.pool.HikariPool.getConnection(...)
    at com.zaxxer.hikari.HikariDataSource.getConnection(...)

What the thread states mean:

  • RUNNABLE — Actively executing (CPU work)
  • BLOCKED — Waiting for a monitor lock (synchronized block)
  • WAITING — Waiting indefinitely (Object.wait, Thread.join)
  • TIMED_WAITING — Waiting with timeout (common for pool timeouts)

Many threads in TIMED_WAITING on pool acquisition = connection pool exhaustion. Increase pool size or reduce query hold time.

Load Testing Diagnostics

The /api/loadtest endpoint is designed for use with Azure Load Testing or similar tools to generate realistic load patterns that can trigger Azure App Service timeout behavior.

What Happens Under Load

  1. Response Time Degradation: As concurrent requests exceed the soft limit (default: 25), response times increase linearly based on the degradation factor
  2. Memory Pressure: Each request holds a memory buffer (default: 20MB). With many concurrent requests, this creates visible memory pressure in Azure metrics
  3. Exception Injection: After errorAfter seconds of processing (default: 120), requests have an errorPercent chance per cycle (default: 20%) of throwing a random exception. Errors are injected after thread blocking delays for chaotic, unpredictable timing.
  4. Frontend Timeout: At high enough load, requests may exceed the Azure App Service stamp frontend 230-second timeout

Monitoring Load Tests

Azure Monitor Metrics

  • Response Time: Watch P95/P99 increase as load exceeds soft limit
  • Memory Working Set: Grows proportionally to concurrent requests
  • HTTP Server Errors: Increases after requests run for errorAfter seconds (default: 120)
  • Average Response Time: Should show clear degradation curve

Application Insights

  • Failed Requests: Look for injected exception types (TimeoutException, IOException, etc.)
  • Request Duration: Create charts showing duration distribution
  • Exceptions: Search for "[Injected after" to find simulated failures

KQL Queries for Load Testing

Load Test Response Time Degradation

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where CsUriStem == "/api/loadtest"
| summarize 
    Count=count(),
    AvgDuration=avg(TimeTaken),
    P95Duration=percentile(TimeTaken, 95),
    ErrorCount=countif(ScStatus >= 500)
    by bin(TimeGenerated, 1m)
| render timechart

Injected Exceptions

AppServiceConsoleLogs
| where TimeGenerated > ago(1h)
| where ResultDescription contains "[Injected after"
| project TimeGenerated, ResultDescription
| order by TimeGenerated desc

Concurrent Request Correlation

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where CsUriStem == "/api/loadtest"
| summarize ConcurrentRequests=count() by bin(TimeGenerated, 1s)
| join kind=inner (
    AppServiceHTTPLogs
    | where CsUriStem == "/api/loadtest"
    | summarize AvgDuration=avg(TimeTaken) by bin(TimeGenerated, 1s)
) on TimeGenerated
| project TimeGenerated, ConcurrentRequests, AvgDuration
| render timechart

Stats Endpoint

Use GET /api/loadtest/stats to monitor load test progress:

  • currentConcurrent: Active requests right now
  • peakConcurrent: Maximum concurrent requests seen
  • errorRate: Percentage of failed requests
  • avgResponseTimeMs: Mean response time in current period
  • requestsPerSecond: Current throughput

Stats are logged to the event log every 60 seconds with type LOAD_TEST_STATS.

Best Practices

Start Small

Begin with short duration simulations (10-30 seconds) and low intensity (2-4 workers, 100-200MB memory) to understand baseline impact before scaling up.

Monitor Before Simulating

Establish a baseline by observing metrics for a few minutes before starting any simulation. This makes it easier to identify changes.

Production Caution

Never run crash simulations or high-intensity stress tests in production environments. Use staging/development slots for testing.
