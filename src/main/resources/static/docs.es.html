🎯 Simulador de Problemas de Rendimiento

Una aplicación educativa Azure App Service que crea intencionadamente problemas de rendimiento con fines de aprendizaje y demostración.

Propósito

Esta aplicación está diseñada para ayudar a Azure App Service Ingenieros de Soporte y Asesores Técnicos:

📖
Aprende

Cómo diagnosticar problemas comunes de rendimiento en Azure App Service

🔧
Práctica

Uso de Azure herramientas de diagnóstico y monitorización

🎭
Demostrar

Anti-patrones de rendimiento en un entorno controlado

👥
Tren

Apoyar a los equipos en la identificación y resolución de problemas de rendimiento

⚠️ Advertencia — ¡Esta aplicación crea intencionadamente problemas de rendimiento!
  • 🔥 CPU estrés — Genera hilos de trabajo que ejecutan operaciones criptográficas para consumir CPU núcleos
  • 📊 Presión de memoria — Asigna y mantiene grandes arrays de bytes para aumentar el uso del montón
  • 🟣 Falta de hilo — Bloquea hilos servlet con operaciones síncronas
  • 🔌 Agotamiento del pool de conexión — Simula la saturación de la piscina de conexión JDBC
  • 💥 Caídas de aplicaciones — Activa errores fatales en pruebas Azure Monitorización de Accidentes
  • ❌ Solicitudes fallidas — Genera HTTP errores 5xx para probar AppLens y Application Insights
🛡️ Aviso de seguridad: Solo despliega esta aplicación en entornos aislados y no de producción.

CPU Simulación de tensiones

Cómo funciona

La simulación de CPU tensión crea hilos de trabajo que funcionan PBKDF2WithHmacSHA512 operaciones criptográficas—trabajo computacionalmente costoso que no puede ser optimizado por el compilador JIT.

Comprendiendo la simulación

Cada hilo de trabajo se ejecuta en un bucle cerrado realizando operaciones de hash de contraseñas. Esto imita escenarios del mundo real como:

  • Algoritmos ineficientes — Bucles O(n²) o retroceso regex
  • Cachés faltantes — Recalculando repetidamente operaciones costosas
  • Malware de minería de criptomonedas— Consumo no autorizado de CPU
  • Consultas no optimizadas — Procesamiento de datos CPUenlazado

Opciones de configuración

  • Duración (segundos) — Cuánto tiempo dura el estrés antes de detenerse automáticamente.
  • Intensidad — Elige Alto o Moderado para controlar CPU nivel de consumo.

Lo que verás en Diagnósticos

  • Volcados de hilos: Hilos en RUNNABLE Estado dentro PBKDF2Core o SecretKeyFactory
  • CPU Perfilador: Muestras de alta CPU en clases criptográficas
  • App Service Métricas:CPU pico porcentual durante la simulación

Controles del salpicadero

Utiliza el CPU Estrés Panel en el salpicadero para iniciar/detener simulaciones. Selecciona nivel de intensidad y duración, luego haz clic Desencadenante CPU estrés.

Simulación de presión de memoria

Cómo funciona

La simulación de memoria asigna grandes arrays de bytes que se mantienen en el montón hasta que se liberan explícitamente, impidiendo que la recogida de basura recupere la memoria.

Comprendiendo las fugas de memoria

En aplicaciones reales, las fugas de memoria ocurren cuando los objetos permanecen accesibles pero ya no se necesitan. Las causas más comunes incluyen:

  • Colecciones estáticas — Sumando a una estática List o Map sin eliminar
  • Oyentes del evento — Registro de oyentes que nunca son dados de baja
  • Cachés sin desalojo — Cachés ilimitados que crecen indefinidamente
  • Variables ThreadLocal — Valores mantenidos en hilos agrupados
  • Datos de la sesión— Objetos grandes almacenados en sesiones HTTP

Opciones de configuración

  • Tamaño (MB) — Cantidad de memoria heap para asignar por clic. Múltiples asignaciones se acumulan.

Lo que verás en Diagnósticos

  • GC Frecuencia: Aumento de la actividad GC a medida que se llena el montón
  • Vertidos de montones: Grande byte[] Matrices conservadas por el servicio de simulación
  • Métricas de memoria: Uso del heap ascendiendo hacia el objetivo configurado
  • GC Pausa: Más tiempos GC a medida que el montón se acerca a su capacidad

Controles del salpicadero

Utiliza el Memoria panel en el panel para asignar memoria y ver cómo el uso del montón crece en tiempo real. Clic Lanzamiento liberar toda la memoria asignada bajo demanda.

Simulación de inanición de Pool de Hilos

Nota: Esto es el equivalente en Java de "Event Loop Blocking" en Node.js. Dado que Java utiliza un modelo de hilo por solicitud, bloquear múltiples hilos servlet simula El mismo síntoma de la cola de peticiones y los picos de latencia.

Comprendiendo la duración y el recuento de hilos

La simulación genera peticiones internas de HTTP que cada una bloquee un hilo servlet. Así es como funciona el tiempo:

  • Duración por solicitud: Cada solicitud de bloqueo se ejecuta durante la duración especificada (por ejemplo, 10 segundos)
  • Pool de hilos Tomcat: Máximo por defecto ~200 hilos
  • Comportamiento ondulatorio: Si generas más hilos que el tamaño del pool, las solicitudes excedentes se colocan en la cola de HTTP de Tomcat

Ejemplo de línea temporal (220 hilos, duración de 10 segundos):

Tiempo ¿Qué pasa
0-10 Las primeras 200 peticiones, agarra los hilos, empieza a bloquear. 20 solicitudes esperando en la cola.
~10s La primera oleada completa. Ahora tengo 20 solicitudes en cola y ahora tienen hilos.
~Años 20 La segunda oleada completa. La simulación termina.

Fórmula: Tiempo total ≈ durationSeconds × ⌈threadCount / 200⌉

Opciones de configuración

  • Hilos bloqueados — Número de solicitudes de bloqueo que aparecen
  • Duración (segundos) — Cuánto tiempo bloquea cada solicitud su hilo

Configuraciones recomendadas:

  • Prueba rápida: 150 hilos, 10 segundos (una sola onda, ~10 segundos en total)
  • Impacto moderado: 200 hilos, 15s (satura pool, ~15s en total)
  • Prueba ampliada: 400 hilos, 10 segundos (dos oleadas, ~20 segundos en total)

Lo que verás en Diagnósticos

  • Volcados de hilos: Muchos hilos en TIMED_WAITING Estado
  • Picos de latencia: Las nuevas solicitudes se colocan detrás de hilos bloqueados
  • Panel de control: El recuento de hilo activo aumenta rápidamente

Agotamiento de la piscina de conexión

Comprensión de los Pools de Conexión

Los pools de conexiones de bases de datos (como HikariCP, C3P0, Tomcat JDBC) mantienen un número fijo de conexiones reutilizables a bases de datos. Cuando todas las conexiones están en uso, las nuevas solicitudes deben esperar. Este es uno de los problemas de rendimiento más comunes en las aplicaciones Java.

Cómo funciona esta simulación

Nosotros usamos un Semáforo — una primitiva de concurrencia en Java que controla el acceso a un número limitado de recursos. Piénsalo como un aparcamiento:

  • Tamaño de la piscina = Número de plazas de aparcamiento
  • acquir() = El coche ocupa un espacio (obtiene una conexión)
  • Release() = Coche se va (devuelve la conexión al pool)
  • Hilos de espera = Coches que hacen cola en la puerta cuando el aparcamiento está lleno

Semáforo → Mapeo HikariCP:

new Semaphore(10) maximumPoolSize=10
tryAcquire(30, SECONDS) connectionTimeout=30000
release() Conexión restablecida a la piscina
Hilo bloqueado al adquirir Hilo esperando conexión disponible

Opciones de configuración

Ajustable a través del salpicadero:

  • Tamaño de la piscina — Número de conexiones simuladas disponibles
  • Duración de la consulta (segundos) — Cuánto tiempo mantiene cada \"consulta\" una conexión
  • Consultas concurrentes — Número de consultas simultáneas a intentar
  • Tiempo de espera de conexión (segundos) — Cuánto tiempo esperar antes de que se agote el tiempo

Lo que verás en los dumps de hilos

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)
    at com.microsoft.azure.samples.perfsimjava.service.ConnectionPoolService.executeQuery(...)
    ...

En aplicaciones reales, esto se notaría HikariPool.getConnection() o BasicResourcePool.getResource() en su lugar.

Indicadores diagnósticos

  • Los volcados de hilos muestran hilos TIMED_WAITING en Semaphore.tryAcquire
  • Picos de latencia cuando los hilos servlet bloquean la espera de conexiones
  • Errores de tiempo de espera cuando la espera supera el tiempo de espera configurado
  • El panel muestra la utilización en tiempo real de la piscina y el número de tiempos de espera

Simulación de solicitudes fallidas

Cómo funciona

La simulación de Solicitudes Fallidas genera HTTP errores 5xx realizando peticiones internas al punto final de la prueba de carga con una probabilidad de error del 100%. Cada solicitud genera un error visible del servidor que aparece en Azure diagnóstico.

Comprendiendo HTTP errores 5xx

HTTP errores 5xx indican fallos en el lado del servidor. Esta simulación te ayuda a practicar la identificación y diagnóstico de patrones de error usando Azure herramientas:

  • AppLens:HTTP errores 5xx aparecen en la línea de tiempo de disponibilidad y en los informes de errores
  • Application Insights: Las solicitudes fallidas se registran con detalles de excepción completa
  • Azure Monitor: La métrica http5xx aumenta, activando cualquier alerta configurada
  • Análisis de registros: Detalles de error disponibles mediante consultas KQL

Opciones de configuración

  • Número de solicitudes — Cuántas solicitudes fallidas deben generarse (1-1000, por defecto: 10)

Lo que verás en Diagnósticos

  • AppLens:HTTP aumento de error 5xx en la cronograma, caída de disponibilidad
  • Application Insights: Solicitudes fallidas con tipos de excepción como TimeoutException, IOException
  • Azure Monitor: Incremento de la métrica Http5xx
  • Latencia de solicitudes: Cada solicitud tarda ~2+ segundos en ejecutarse antes de fallar

API Endpoint

POST /api/simulaciones/fallidos-solicitudes

Activa un lote de solicitudes de error 5xx HTTP .

Cuerpo de la solicitud:

{
    "numberOfRequests": 10
}

Respuesta:

{
    "simulationId": "abc123",
    "type": "FAILED_REQUESTS",
    "numberOfRequests": 10,
    "status": "RUNNING",
    "message": "Generating 10 failed HTTP requests"
}

Controles del salpicadero

Utiliza el Solicitudes fallidas panel en el panel de control para generar errores. Introduce el número de solicitudes y haz clic Generar errores. La simulación se ejecuta rápidamente y produce HTTP respuestas 5xx visibles en Azure herramientas de diagnóstico.

Simulación de accidentes

Advertencia: Estas simulaciones se bloquean o terminan la aplicación. Úsalo solo para probar diagnósticos y escenarios de recuperación en App Service.

Tipos de accidentes disponibles

Selecciona un tipo de fallo desde el panel para probar diferentes modos de fallo:

🛑 Fallo rápido (System.exit)

Termina inmediatamente la JVM con System.exit(1). El proceso sale sin ejecutar ganchos de cierre ni finalizadores. En App Service, esto provoca un reinicio inmediato.

📉 Desbordamiento de pila

Activa un StackOverflowError a través de recursión infinita. Esto simula errores como llamadas circulares a métodos o recursión ilimitada. La traza de pila mostrará llamadas repetidas al mismo método.

⚠️ Excepción no resuelta

Lanza un sin control RuntimeException De un gestor de solicitudes. Prueba cómo tu aplicación gestiona errores inesperados y si el middleware de gestión de excepciones funciona correctamente.

💥 Fuera de la memoria (OOM)

Asigna memoria rápidamente hasta que la JVM lanza un OutOfMemoryError. Esto es útil para hacer pruebas:

  • App Service comportamiento de reinicio automático en OOM
  • Alerta y monitorización de memoria
  • Configuración de la colección de volcado de heap

Configuración opcional

Puedes personalizar el comportamiento de la aplicación usando Azure App Service variables de entorno.

Tasa de Prueba de Salud

Controla con qué frecuencia el servidor envía sondas de salud para medir la latencia de las solicitudes. Todas las sondas se enrutan a través del frontend Azure para capturar latencias realistas de extremo a extremo.

Variable de entorno

Nombre de la variable Descripción Default
HEALTH_PROBE_RATE Intervalo de sonda en milisegundos. Mínimo 100ms. 200

Configuración mediante Azure CLI

# Slow down probes if CLR profiler shows overlapping requests
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings HEALTH_PROBE_RATE=400

Tiempo de espera en reposo

Cuando la aplicación está inactiva (sin conexiones al panel ni solicitudes de pruebas de carga), las sondas de salud se suspenden automáticamente para reducir el tráfico de red innecesario al frontend de Azurey a la telemetría Application Insights .

Variable de entorno

Nombre de la variable Descripción Default
IDLE_TIMEOUT_MINUTES Minutos de inactividad antes de suspender las sondas de salud. La actividad se reanuda automáticamente cuando se abre el panel de control o se recibe cualquier solicitud. 20

Configuración mediante Azure CLI

# Extend idle timeout to 30 minutes
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings IDLE_TIMEOUT_MINUTES=30

Pie de página personalizado

Establece un mensaje personalizado en el pie de página que aparezca en todas las páginas. El pie de página soporta HTML, lo que permite incluir enlaces.

Variable de entorno

Nombre de la variable Descripción
PAGE_FOOTER Contenido HTML para la segunda línea del pie de página. Si no está activado, solo se muestra la descripción de la app y la información de la build.

Valor de ejemplo

Created by <a href="https://yoursite.com">Your Team</a> for training purposes

Configuración mediante Azure CLI

# Set the footer via Azure CLI
az webapp config appsettings set --name $APP_NAME --resource-group $RESOURCE_GROUP \
  --settings 'PAGE_FOOTER=Created by <a href="https://yoursite.com">Your Team</a> for training purposes'

Ambientación a través de Azure Portal

  1. Navega hasta tu App Service en el Portal Azure
  2. Ir a Escenarios → Variables de entorno
  3. Clic + Añadir
  4. Nombre del conjunto: PAGE_FOOTER
  5. Valor fijado: Contenido del pie de página HTML
  6. Clic Solicita, entonces Confirmar

Arquitectura

La aplicación funciona como una aplicación Spring Boot 3.3 con Tomcat integrado, STOMP sobre WebSocket para métricas en tiempo real y estado en memoria. Un servicio de sonda dedicado mide la latencia de la solicitud sondeando la aplicación a través del frontend de Azure.

Componentes clave

  • Aplicación Spring Boot— Servidor Tomcat embebido con controladores REST y soporte WebSocket
  • Servicio de sonda— Tarea programada en segundo plano que mide la latencia de la solicitud enviando sondas HTTP a través del frontend Azure
  • Servicios de simulación — CPU simulaciones de estrés, presión de memoria y bloqueo de hilos se ejecutan en pools de hilos dedicados para evitar privar los hilos servlet
  • WebSocket Broker — Mensajería STOMP vía SockJS para actualizaciones en tiempo real del panel de control (métricas, eventos, estado de la simulación)

🌐 Selección de idioma

La interfaz del panel de control puede mostrarse en cualquier idioma soportado por Azure Traductor de Servicios Cognitivos. La traducción se realiza una vez al iniciar la aplicación y se almacena en caché — no hay ninguna sobrecarga de traducción en tiempo de ejecución.

Cómo funciona

  1. Establece el UI_LANGUAGE Variable de entorno a un código de idioma ISO 639-1 (por ejemplo, es, fr, ja, zh-Hans)
  2. Proporcionar credenciales de traductor Azure a través de variables de entorno
  3. Al iniciar, la app traduce todas las cadenas de la interfaz (en.json → {lang}.json) y páginas de documentación HTML
  4. Los archivos traducidos se almacenan en caché con un hash SHA-256 del código fuente — solo se retraducen cuando el código fuente cambia

Variables de entorno requeridas

Variable Descripción Default
UI_LANGUAGE Código en el idioma de destino en (sin traducción)
TRANSLATOR_API_KEY Azure Traductor API clave —
TRANSLATOR_ENDPOINT Punto final de servicio traductor https://api.cognitive.microsofttranslator.com
TRANSLATOR_REGION Azure región del recurso traductor eastus

Azure App Service Configuración

En el portal Azure , ve a tu App Service → Configuración → Configuración de aplicación y añadir:

UI_LANGUAGE=es
TRANSLATOR_API_KEY=your-key-here
TRANSLATOR_REGION=eastus

Términos protegidos

Términos técnicos listados en locales/no-translate.json (por ejemplo, "Azure App Service", "CPU", "JVM", "STOMP") se envuelven automáticamente en <span class="notranslate"> etiquetas antes de traducir, asegurándose de que permanezcan en inglés independientemente del idioma de destino.

Comportamiento de la caché

  • Los archivos de localización traducidos se almacenan como locales/{lang}.json (por ejemplo, locales/es.json)
  • Los documentos HTML traducidos se almacenan como {name}.{lang}.html (por ejemplo, docs.es.html)
  • Cada archivo en caché incluye un hash SHA-256 del código fuente — si el código fuente en inglés no ha cambiado, se omite la traducción
  • Elimina el archivo en caché para forzar la retraducción en el siguiente reinicio
