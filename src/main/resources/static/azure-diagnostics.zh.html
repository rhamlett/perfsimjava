诊断 Azure 工具性能问题指南

概述

本指南将解释如何使用 Azure 诊断工具分析该应用模拟的性能问题。

🔗 仿真ID相关性

每个仿真实例都被分配一个唯一的仿真ID（GUID），以实现端到端的相关性 在仪表盘界面和 Azure Application Insights 遥测之间。

寻找仿真ID

在仪表盘中： 事件日志中的仿真开始和完成消息具有 细微的虚线下划线表示它们是互动的。将鼠标悬停在这些消息上可查看完整内容 提示中的仿真ID。点击复制到你的剪贴板。

Azure： 相同的仿真ID也出现在服务器端日志中，并可在以下格式中找到：

  • Application Insights — 按仿真ID搜索痕迹和自定义事件
  • 日志分析 — 使用ID作为筛选器的查询日志
  • App Service 日志— 按 GUID 过滤标准/标准

相关性查询

在Log Analytics中使用这些KQL查询，将仪表盘事件与服务器遥测数据关联起来：

⚠️ 表格名称差异

Log Analytics 工作区使用与经典 Application Insights不同的表和列名。 如果你看到诸如“'traces'名称不指向任何已知表”这样的错误，请使用下面的Log Analytics名称：

应用洞察 日志分析
tracesAppTraces
customEventsAppEvents
requestsAppRequests
exceptionsAppExceptions
dependenciesAppDependencies
messageMessage
timestampTimeGenerated
customDimensionsProperties
 
// Find simulation start/end events by Simulation ID
AppEvents
| where Name in ("SimulationStarted", "SimulationEnded")
| where Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
| project TimeGenerated, Name, Properties
| order by TimeGenerated asc
// Find all requests during a simulation time window
let simStart = toscalar(
    AppEvents 
    | where Name == "SimulationStarted" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
let simEnd = toscalar(
    AppEvents 
    | where Name == "SimulationEnded" and Properties["SimulationId"] == "YOUR-SIMULATION-ID-HERE"
    | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| order by TimeGenerated asc
// Find failed requests during a simulation
let simId = "YOUR-SIMULATION-ID-HERE";
let simEvents = AppEvents | where Properties["SimulationId"] == simId;
let simStart = toscalar(simEvents | where Name == "SimulationStarted" | project TimeGenerated);
let simEnd = toscalar(simEvents | where Name == "SimulationEnded" | project TimeGenerated);
AppRequests
| where TimeGenerated between (simStart .. simEnd)
| where Success == false
| project TimeGenerated, Name, ResultCode, DurationMs, Url
| order by TimeGenerated asc

故障排除工作流程

  1. 从仪表盘开始模拟
  2. 将鼠标悬停在事件日志中的开始消息上，复制模拟ID
  3. 打开 Azure 门户→ Application Insights →日志（或日志分析）
  4. 使用仿真ID查询日志，查看所有相关的服务器端活动
  5. 将仪表盘事件与服务器指标的时间戳关联起来

💡 提示

仿真ID有助于在运行多个并发仿真时隔离遥测数据，或者 当仪表盘被多个用户使用时。

AppLens 整合

该应用设计为与 Azure AppLens 工作，每100毫秒发送健康探针 通过 Azure Stamp前端。这种高频探测确保了延迟的尖峰和 可用性问题在 AppLens 仪表盘中可见。

AppLens能检测到什么

  • CPU 压力： 高 CPU 利用率图表，潜在限速警报
  • 记忆压力： 内存使用激增，潜在的 OOM 模式
  • 线索匮乏： 请求延迟增加，请求队列
  • 连接池： 线程转储显示等待状态，超时错误
  • 未通过的请求：HTTP 5xx 错误峰值、可用性下降、错误率增加
  • 崩溃情况： 实例重启，可用性下降

Azure 监测指标

运行模拟时 Azure 监测中需要关注的关键指标：

平台指标

  • CPU 百分比： 在 CPU 应力模拟中注意尖峰
  • 记忆工作组： 内存压力模拟期间的增加
  • HTTP 排队长度： 线材匮乏时生长
  • 响应时间： 注意P95/P99延迟增加
  • http 5xx： 请求失败和崩溃模拟期间的增加

JVM 指标（如果启用了 App Insights）

  • jvm_memory_used： 堆内存与非堆内存
  • jvm_gc_pause：GC暂停时间
  • jvm_threads_live： 主动线程计数

Application Insights

如果 Application Insights 已配置，您可以使用以下功能：

实时指标流

在模拟过程中观看实时指标：

  1. 在Azure门户中导航到你的App Service
  2. 前往 Application Insights →实时指标
  3. 实时观察 CPU、内存和请求速率

交易搜索

查找慢或失败的请求：

  1. 前往 Application Insights →交易搜索
  2. 按“失败请求”或“服务器响应时间>5秒”筛选
  3. 深入挖掘单个请求，查看时间分布

应用地图

可视化服务健康状况和依赖关系：

  1. 前往 Application Insights →申请地图
  2. 在模拟中注意红黄指示
  3. 检查故障率或延迟是否增加

诊断与解决问题

Azure App Service 提供了内置的诊断工具：

可用性与性能

  1. 前往 App Service → 诊断与解决问题
  2. 选择“可用性和性能”
  3. 查看“HTTP 5xx 错误”以了解崩溃相关的问题
  4. 检查“高 CPU”以获得 CPU 应力检测
  5. 检查“内存”以检测内存压力

诊断工具

  • CPU 深入分析： 请参见 CPU 实例的使用分解
  • 内存转储： 内存问题期间的捕获堆转储
  • 帖子倾倒： 饥饿期间的捕获线程堆栈
  • JFR（爪哇飞行记录仪）： 配置文件 Java 应用

日志分析 / KQL 查询

用于分析仿真效应的实用KQL查询：

高 CPU 请求

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where ScStatus >= 500
| summarize Count=count() by bin(TimeGenerated, 1m)
| render timechart

响应时间缓慢

AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| where TimeTaken > 5000
| project TimeGenerated, CsUriStem, TimeTaken, ScStatus
| order by TimeTaken desc

内存使用模式

AppServicePlatformLogs
| where TimeGenerated > ago(1h)
| where Level == "Informational"
| project TimeGenerated, Message
| order by TimeGenerated desc

Java 专用诊断

启用JMX进行远程监控

为JMX访问（仅开发）添加以下应用设置：

JAVA_OPTS=-Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9010 \
  -Dcom.sun.management.jmxremote.local.only=false \
  -Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false

启用 GC 日志

JAVA_OPTS=-Xlog:gc*:file=/home/LogFiles/gc.log:time,level,tags

堆积倾倒 OOM

JAVA_OPTS=-XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/home/LogFiles/heapdump.hprof

读取线程转储：连接池耗尽

诊断连接池问题时，要注意线程 TIMED_WAITING 资源获取时被封锁状态：

"http-nio-8080-exec-42" #42 daemon prio=5 TIMED_WAITING
    at jdk.internal.misc.Unsafe.park(Native Method)
    at java.util.concurrent.locks.LockSupport.parkNanos(...)
    at java.util.concurrent.Semaphore.tryAcquire(...)

真实的HikariCP示例：

"http-nio-8080-exec-15" TIMED_WAITING
    at com.zaxxer.hikari.pool.HikariPool.getConnection(...)
    at com.zaxxer.hikari.HikariDataSource.getConnection(...)

帖子里说的意思是：

  • 可跑 —— 积极执行（CPU 工作）
  • 被封锁 — 等待监视器锁（同步块）
  • 等待 — 无限期等待（Object.wait， Thread.join）
  • TIMED_WAITING — 带暂停等待（泳池暂停常见）

TIMED_WAITING中许多线程关于池获取 = 连接池耗尽。增加查询池大小或缩短查询等待时间。

最佳实践

从小处开始

从短时间（10-30秒）和低强度的模拟开始 （2-4名工作者，100-200MB内存）以便在扩展前了解基线影响。

模拟前先监控

在比赛前观察几分钟的指标，建立基线 开始任何模拟。这使得识别变化变得更容易。

制作注意

绝不要在生产环境中运行碰撞模拟或高强度压力测试 环境。使用分期/开发时段进行测试。
